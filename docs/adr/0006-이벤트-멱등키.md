# 0006. 이벤트 멱등키: (도입사, transaction_id) 유일

- 상태: 제안
- 결정일: 2026-07-29 (데일리 비준, PR 머지 시 승인으로 변경)
- 관련 이슈: MS2-26

## 맥락

같은 transaction_id가 "중복"으로 판정되는 범위를 정해야 한다. 이 범위는 이벤트 테이블의 유니크 제약이 되는데, 중복 허용 범위를 줄이는 방향(제약 강화)으로는 위반 데이터가 이미 쌓여 있을 수 있어 되돌릴 수 없고, raw 이벤트가 불변(0008)이라 재발급도 불가능하다. v0 도메인 모델은 (도입사, 구독, transaction_id)를 제안했지만 S1 ERD에는 구독 엔티티가 없다.

## 결정

transaction_id는 (organization_id, transaction_id)로 도입사 안에서 전역 유일하다. 기간 윈도우는 두지 않는다(무기한 유일). 형식 규칙: 불투명 문자열로 취급해 바이트 단위 정확 일치(대소문자 구분)로 비교하고, 서버는 트림이나 대소문자 변환 같은 해석과 정규화를 하지 않는다. 빈 값 금지, 길이 상한 255자.

지금 정하지 않는 것:

- 중복 재전송의 응답 규약(200과 최초 결과 반환 등)은 API 명세(MS2-27, `docs/api/openapi.yaml`) 소관이다
- 구독 도입 시 (도입사, 구독, transaction_id)로의 완화는 그 시점에 결정한다

## 근거

- 테넌트 격리가 1순위다. 플랫폼 전역 유일은 A도입사의 transaction_id가 B도입사의 이벤트를 막을 수 있어 탈락이고, 격리를 지키는 안 중 S1에서 구현 가능한 것은 이 안뿐이다
- 되돌리기 방향이 안전하다. 이 제약을 만족하는 데이터는 구독 포함 제약을 항상 만족하므로, 구독 도입 시점의 완화가 재적재 없이 가능하다(단일 컬럼 backfill 수준 비용)
- 도입사 부담이 합리적이다. 자기 시스템 안에서만 유일하게 발급하면 되고(UUID면 충분), 타사와 겹치지 않게 발급할 필요가 없다
- 기간 윈도우는 "언제부터 재사용 가능한가"를 클라이언트가 추적하게 만들어 멱등의 의미를 약화시키므로 도입하지 않는다
- 형식 규칙도 불변인 이유: "두 ID가 같다"의 정의가 곧 유니크 제약의 실질 의미이며, 대소문자 구분을 비구분으로 바꾸는 것은 제약 강화 방향이라 기존 데이터에 충돌이 생길 수 있다. 길이 상한은 인덱스 비대와 악의적 초장문 ID 방지

## 대안

- 플랫폼 전역 유일 `UNIQUE(transaction_id)`: 테넌트 격리가 깨져 배제
- (도입사, 구독, transaction_id): v0 원안이지만 S1에 구독이 없어 구현 불가. 이쪽에서 시작하면 나중에 좁히는 방향 전환이 사실상 불가역이라, 좁게 시작해 넓히는 현재 안이 안전하다

## 전환 조건

- 이벤트 테이블에 시간 파티셔닝을 도입하는 시점: PostgreSQL은 파티션 테이블의 유니크 인덱스에 파티션 키 포함을 요구하므로 무기한 전역 유일을 유지할 수 없다. 그 시점에 기간 윈도우 도입과 함께 재검토하고 새 ADR로 기록한다
- 구독 도입 시점: (도입사, 구독, transaction_id)로 완화할 수 있으나, 기존 행의 구독 컬럼 backfill 또는 NULLS NOT DISTINCT 인덱스가 필요하고, 그동안 거절되던 재전송 패턴이 통과하게 되어 관측 동작이 바뀐다는 점을 인지하고 완화한다
