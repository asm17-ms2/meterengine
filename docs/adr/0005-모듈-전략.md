# 0005. 모듈 전략: 모듈러 모놀리스 지향, 단계적 경계 강제

- 상태: 승인
- 결정일: 2026-07-29
- 관련 이슈: MS2-28

## 맥락

배포 단위와 코드 내부 구조를 정해야 한다. 수집(ingestion)은 장기적으로 처리량 요구가 달라 분리 후보지만, 3인 팀이 S1을 1주에 완주해야 하는 지금 서비스 분리는 과하다. 상세 규칙 초안은 Notion Engineering Wiki의 "백엔드 모듈 규칙" 문서에 있고, 이 ADR은 그 요약과 단계 전환 조건을 기록한다.

## 결정

배포 단위는 서버 하나(모놀리스)로 하되, 코드 내부는 도메인 모듈 경계에 가깝게 유지한다. S1에서는 단일 Gradle 모듈 + 도메인별 패키지 분리로 시작하고, 경계는 도구로 강제하지 않고 코드 리뷰로만 지킨다. 경계 강제 장치는 단계적으로 올린다.

1. S1: 단일 Gradle 모듈 + 도메인별 패키지 분리, 코드 리뷰로 강제
2. 패키지 구조 안정 후: Spring Modulith 도입, CI에서 경계 위반 검증
3. 경계가 확실해진 도메인부터 Gradle 멀티모듈 승격
4. 실측된 필요가 생길 때만 별도 서비스 분리

지금 정하지 않는 것:

- 도메인 패키지 목록은 슬라이스를 진행하며 도출한다 (S1 예상: ingestion, metering, pricing, billing, common이나 확정 아님)
- 서비스 분리 시의 통신 방식 상세는 분리 시점에 결정한다

## 근거

- 3인 팀에서 서비스 분리는 배포/관측/장애 대응 비용이 기능 개발을 압도한다. walking skeleton을 빨리 통과시키는 것이 S1의 목적이다
- 반대로 경계 없는 모놀리스는 나중에 떼어낼 수 없게 된다. 분리 후보(ingestion)가 이미 보이므로, 경계를 패키지 수준에서라도 유지해 두면 분리 비용이 선형으로 유지된다
- 처음부터 도구로 강제하지 않는 이유: 도메인 경계 자체가 아직 미확정이라, 경계가 틀렸을 때 고치는 비용이 낮은 리뷰 강제 단계에서 구조를 학습하는 편이 낫다
- 기술 스택(0001)과 정합한다: Spring Modulith라는 검증된 상향 경로가 있다

## 대안

- 처음부터 마이크로서비스: 이 규모에서 운영 비용이 정당화되지 않고, 도메인 경계 미확정 상태의 분리는 잘못된 경계를 네트워크 경계로 고착시킨다
- 처음부터 Gradle 멀티모듈: 경계 위반이 컴파일 에러가 되는 장점은 있지만, 경계가 틀렸을 때 재편 비용이 커서 구조 학습 전에는 이르다
- 경계 없는 단일 모놀리스: 가장 빠르지만 ingestion 분리 시점에 사실상 재작성이 된다

## 전환 조건

- S1 종료 후 패키지 구조가 안정되면 Spring Modulith를 도입한다 (2단계 상향)
- 특정 도메인의 경계 위반이 리뷰에서 반복 관측되면 해당 도메인부터 Gradle 멀티모듈로 승격한다 (3단계 상향)
- 특정 모듈의 처리량이나 배포 주기 요구가 실측으로 확인될 때만 서비스로 분리한다 (4단계, 0002/0003의 전환 조건 도달과 연동될 가능성이 높다)
