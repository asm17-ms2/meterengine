# 0006. 데이터 접근: 기본은 JPA, 원장과 집계 SQL은 JdbcClient

- 상태: 제안
- 결정일: 2026-07-31
- 관련 이슈: MS2-38

## 맥락

기술 스택 확정(ADR 0001) 때 DB 접근은 Spring Data JPA로 선언했다. 첫 구현 스토리(MS2-38)에서 usage_events 저장소를 만들며, 이 테이블의 성격이 JPA의 기본 동작과 세 지점에서 어긋나는 것을 확인했다.

- DB 생성 값: id는 `gen_random_uuid()`, received_at은 트리거가 서버 시각으로 덮어쓴다 (MS2-26 결정, ERD v2). 값이 INSERT 후에야 존재한다
- 충돌이 정상 흐름: 멱등 재전송의 유니크 충돌은 에러가 아니라 "200으로 기존 이벤트를 돌려줄" 비즈니스 경로다 (결정 4, first-write-wins)
- 불변 강제 트리거: UPDATE/DELETE가 DB에서 거부된다 (결정 3)

첫 도메인 코드가 팀 관례를 사실상 정하므로, 어디까지 JPA고 어디부터 SQL인지 경계를 명시해 둔다.

## 결정

기본 데이터 접근은 Spring Data JPA다. 단 다음 두 범위는 Spring Framework의 JdbcClient(spring-jdbc)로 SQL을 직접 쓴다.

- append-only 원장 테이블: usage_events (이후 생기는 동type 원장도 동일)
- 집계 쿼리: 조회 시 raw 이벤트에서 SQL로 계산한다는 ADR 0004의 실행 경로

지금 정하지 않는 것: MyBatis, jOOQ 같은 SQL 매퍼 도입 여부. 손으로 쓰는 SQL이 지금은 2개뿐이라 판단을 미루고, 전환 조건에서 재검토한다.

## 근거

- usage_events는 ORM이 주는 것(변경 추적, 1차 캐시, 연관관계 순회)을 하나도 쓰지 않는다. 접근 패턴이 INSERT 한 문장과 SELECT 한 문장뿐이다
- DB 생성 값은 `INSERT ... RETURNING`으로 자연스럽게 회수된다. JPA로 하려면 `@Generated`(id, received_at)라는 예외 장치가 필요하다 (Hibernate 6+에서 가능함은 확인했다)
- 멱등 경로: JPA는 유니크 충돌이 flush 시점에 터지고 트랜잭션이 rollback-only로 오염되어, insert를 REQUIRES_NEW로 격리해야 "기존 행 조회"를 이어갈 수 있다. JdbcClient 자동커밋 단문에서는 이 문제가 발생하지 않는다 - 충돌 잡고 다음 문장으로 조회하면 끝이다
- 불변 강제와 dirty checking의 충돌: 관리 상태 엔티티의 필드가 실수로 바뀌면 JPA가 UPDATE를 자동 발행하고 트리거가 거부해 뜬금없는 500이 된다. `@Immutable`로 막을 수 있으나 역시 알아야 쓰는 장치다
- 추가 의존성이 없다. spring-jdbc는 이미 클래스패스에 있다 (spring-boot-starter-data-jpa 전이 의존성)

## 대안

- 전부 Spring Data JPA: `@Generated` + `@Immutable` + REQUIRES_NEW 조합으로 구현 가능하다. 스타일 통일과 `ddl-auto=validate`의 스키마 드리프트 감지가 실질 장점이나, 이 테이블에서는 JPA 기본 동작을 하나씩 꺼 가며 쓰는 모양이 된다. CRUD 성격 테이블(customers, meters, price_policies)은 이 대안대로 JPA를 그대로 쓴다 - 그게 이 ADR의 "기본"이다
- Spring Data JDBC: repository 추상화는 얻지만 DB 생성 값 재조회와 jsonb 매핑에 결국 커스텀이 필요하고, Spring Data JPA와 공존시키면 repository 스캔 소속 구분 설정이 추가된다. 팀이 배울 네 번째 스타일이 된다
- MyBatis: 손으로 쓰는 SQL이 수십 개일 때 유효한 도구다. 현재 2개 규모에서는 의존성과 학습 비용이 이득을 넘는다. Spring Boot 4용 starter(4.0)가 초기 단계인 점도 부담이다
- jOOQ: 타입세이프 SQL은 매력적이나 코드 생성 파이프라인 설정이 현 규모 대비 과투자다

## 전환 조건

- 손으로 쓰는 SQL이 집계(MS2-39) 등으로 불어나 매핑과 동적 SQL 부담이 체감되면 MyBatis/jOOQ 도입을 팀 안건으로 올린다
- JPA 엔티티 부재로 인한 스키마-코드 불일치 사고가 실제로 나면 재검토한다 (지금은 Testcontainers 스키마 제약 테스트가 그 역할을 대신한다)
- usage_events에 갱신 성격의 요구가 생기면 재검토한다 - 다만 그 요구 자체가 결정 3(append-only) 위반이므로 먼저 불변 결정 쪽을 다시 논의해야 한다
