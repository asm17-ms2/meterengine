# 0010. 금액과 단가 표현: KRW 정수와 (단가, 묶음 수량) 쌍

- 상태: 제안
- 결정일: 2026-07-29 (데일리 비준, PR 머지 시 승인으로 변경)
- 관련 이슈: MS2-26

## 맥락

금액과 단가의 자료형과 단위를 정해야 한다. 저장된 값의 단위나 자료형을 나중에 바꾸면 전체 재적재라 불변 결정이다. 제약이 하나 있다: 토큰 과금의 실단가는 1토큰당 0.004원 수준이라, 단가까지 원 단위 정수로 강제하면 0원이 되어 성립하지 않는다.

## 결정

- 금액(집계 결과, 요금, 청구 예정액)은 KRW 원 단위 정수(BIGINT)로 저장한다. 컬럼명은 원 단위임이 드러나게 한다(예: amount_krw)
- 단가는 (단가 BIGINT, 묶음 수량 BIGINT) 쌍으로 표현한다. "1,000토큰당 4원" = (4, 1000). per-unit은 unit_size=1의 특수 케이스다
- 단수 계산 구조를 함께 확정한다: 중간 계산(집계 x 단가 / 묶음)은 고정밀로 수행하고 부동소수점을 금지한다. 단수 처리는 정해진 한 지점에서 정확히 1회만 한다. 절사/반올림 선택은 코드에 흩뿌리지 않고 한 곳에 격리한다. 라인아이템에 고정밀 원본값(precise_amount)과 확정 금액을 병행 저장한다
- 절사/반올림 규칙과 적용 지점의 선택값은 이 구조 덕에 가역이므로 여기서 정하지 않는다. 선택은 0013에서 확정한다

## 근거

- 부동소수점은 이진 표현 오차로 합계가 어긋나 과금에 쓸 수 없다
- KRW는 소수 단위(subunit)가 없어 원이 최소 단위다. decimal 자릿수 설계가 공회전한다
- 업계 공통 패턴(2026-07-29 조사): Stripe는 최소 통화 단위 정수, Google Money는 정수 쌍(units+nanos), Lago는 amount_cents BIGINT에 고정밀 precise_amount 병행. 달러도 소수로 저장하는 게 아니라 센트 정수로 저장한다
- 단가 쌍 표현은 Stripe transform_quantity, Google 계열과 같은 방식이다. API 표면이 전부 정수로 유지되고, 정밀도가 unit_size로 명시되며, "1,000토큰당 4원"이라는 가격표 표현 그대로 저장된다
- 다통화 확장은 decimal 전환이 아니라 currency 컬럼 추가(기존 데이터 KRW backfill, 가산적)로 이뤄지므로 이 결정은 해외 확장과 충돌하지 않는다

## 대안

- 전부 decimal: KRW에 소수 단위가 없어 이득이 없고 부동소수점 혼입 위험만 생긴다
- 단가만 NUMERIC 또는 십진 문자열 예외 (Stripe unit_amount_decimal, Lago 계열): 업계 검증된 방식이지만 금액 BIGINT와 자료형이 혼재하고, 단수 발생 지점이 곱셈 즉시로 흩어진다

## 전환 조건

- 다통화 도입 시 currency 컬럼을 추가한다 (자료형 변경 없음)
