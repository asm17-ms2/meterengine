# 0008. raw 이벤트 불변성: append-only와 보상 이벤트 정정

- 상태: 제안
- 결정일: 2026-07-29 (데일리 비준, PR 머지 시 승인으로 변경)
- 관련 이슈: MS2-26

## 맥락

저장된 이벤트를 고치거나 지울 수 있는지, 틀린 이벤트는 어떻게 정정하는지 정해야 한다. raw 이벤트는 모든 청구 금액의 유일한 근거이고, MS2-39 인수 조건 "집계값은 raw에서 재계산해 검증할 수 있다"는 원본이 바뀔 수 있으면 무의미해진다.

## 결정

이벤트 테이블은 append-only다. UPDATE/DELETE를 DB에서 강제로 막는다: 앱 롤에 이벤트 테이블의 UPDATE/DELETE 권한을 주지 않는다. 전제로 마이그레이션/운영 롤과 앱 롤을 분리하고, 앱 롤은 테이블 소유자가 아니어야 한다(소유자에게 REVOKE는 무력).

- 정정은 원본 수정이 아니라 보상(취소/음수) 이벤트를 새로 쌓아서 한다. 보상 이벤트 구현은 후속 슬라이스이고, S1 기간의 정리(테스트 오염 데이터 등)는 운영 롤을 통한 수동 절차로만 하고 그 사실을 기록한다
- 같은 transaction_id로 다른 내용이 재전송되어도 저장본은 절대 바뀌지 않는다(first-write-wins, 이 결정의 따름정리). 내용 불일치 감지용 payload 해시 컬럼은 S1에 두지 않는다. 원문이 보존되므로 언제든 backfill 가능해 불변 결정이 아니다. 불일치 시 응답 규약은 API 명세(MS2-27) 소관이다
- 이벤트 테이블에는 받은 그대로만 저장하고 해석값과 가공값은 별도 파생물로 둔다. 단 하나의 예외는 0007의 해소 컬럼(customer_id, meter_id)으로, NULL을 값으로 1회 채우는 것만 컬럼 단위 권한과 가드 트리거로 허용한다

## 근거

- 청구의 신뢰가 이 위에 선다. 관행상 불변은 "실제로는 삭제 가능"이라 청구 근거가 흔들린다. Lago가 soft delete/수정을 허용한 전철이다
- append-only면 모든 청구 금액을 raw에서 재계산해 검증할 수 있고, 중복 거부가 곧 정확한 집계가 된다
- 보상 이벤트 정정은 해외 빌링 5사의 공통 패턴이다
- 미확인: 롤 분리(마이그레이션/운영/앱)의 구현 담당 스토리가 미정이다. 현재 개발 환경(PR #11)은 단일 계정 구성이라 DB 강제는 아직 걸려 있지 않다

## 대안

- soft delete/수정 허용 (Lago 방식): 감사 가능성이 무너지고 재계산 검증이 성립하지 않아 배제
- 앱 규칙으로만 불변 유지: 코드 실수 한 번에 뚫린다. DB 강제가 아니면 불변이 아니다

## 전환 조건

- 롤 제어가 불가능한 관리형 DB를 택하게 되면 대체 수단(트리거 등)을 새 ADR로 정한다
- 보상 이벤트를 구현하는 슬라이스에서 취소 이벤트의 표현(음수 값, 참조 방식)을 확정한다
