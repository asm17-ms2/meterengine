# 0001. 기술 스택: 백엔드 Java + Spring Boot, 프론트엔드 Next.js

- 상태: 승인
- 결정일: 2026-07-29
- 관련 이슈: MS2-28

## 맥락

MS2-31(개발 환경 구축)과 슬라이스 1 구현 스토리 전체가 스택 확정에 막혀 있다. 레포는 현재 스택 중립 스캐폴딩 상태다. MS2-29 기술 스파이크는 스프린트 2에서 제외됐으므로, 이 결정은 프로토타입 검증 없이 스프린트 1 조사(MS2-22)와 팀 역량 기준으로 내린다.

## 결정

백엔드는 Java 25(LTS) + Spring Boot 4 + Gradle, 프론트엔드(관리자 화면)는 Next.js로 구현한다.

지금 정하지 않는 것:

- 백엔드 세부 라이브러리(DB 접근 방식, 마이그레이션 도구 등)는 MS2-31에서 정한다
- 프론트엔드 세부(상태 관리, UI 라이브러리, 렌더링 방식 활용 범위)는 MS2-46 착수 시점에 정한다

## 근거

- 팀이 공통으로 다룰 수 있는 스택이라는 점을 최우선으로 했다. 스파이크 없이 S1을 1주에 완주해야 하므로 학습 비용이 일정 리스크로 직결된다
- 과금 도메인에 필요한 기반(트랜잭션 관리, DB 제약/마이그레이션, 테스트 도구)이 생태계에서 검증되어 있다
- 모듈 전략(0005)과 맞물린다: 경계 강제가 필요해지는 시점에 Spring Modulith로 단계 상향할 수 있는 경로가 있다. Spring Modulith 2.0이 Spring Boot 4 기반으로 GA되어 있어 이 경로와 버전이 정합한다
- 버전은 작성 시점(2026-07) 기준 지원 현황을 따랐다: Spring Boot 3.5는 2026-06-30에 OSS 지원이 종료됐으므로 신규 프로젝트는 4.x가 기준선이고, Java 25는 현행 최신 LTS다
- 백엔드 모듈 규칙 초안(Notion, Engineering Wiki)이 이 스택을 전제로 작성되어 있다
- 프론트엔드는 React 생태계 중 가장 관례가 잡힌 프레임워크를 택했다. 관리자 화면은 S1에서 조회 전용 최소 화면(MS2-46)이라 프레임워크 선택이 일정에 주는 부담이 작고, 참고 대상 제품들(Lago 등)의 관리자 UI도 React 계열이라 조사 자료를 그대로 참조할 수 있다

## 대안

- Kotlin + Spring: JVM/Spring 생태계는 그대로 얻지만 팀 공통 숙련도가 Java보다 낮아 S1 일정에서 이점이 없다
- Node.js + NestJS: 프론트엔드와 언어 통일이 가능하나 팀 주력이 아니고, 과금 도메인의 정밀 수치 처리에서 얻는 것이 없다
- Python + FastAPI: 빠른 착수는 가능하나 대규모 도메인 모듈 경계 관리 도구가 상대적으로 약하다
- Ruby on Rails: Lago가 검증한 경로지만 팀 경험이 없고, Lago 코드는 AGPL이라 참고 이상으로 쓸 수 없다

프론트엔드 대안:

- Vite + React SPA: 조회 전용 관리자 화면에는 충분하지만, Next.js 대비 라우팅/빌드 관례를 직접 정할 것이 늘어난다
- 백엔드 템플릿 렌더링(Thymeleaf 등): 스택이 하나로 줄지만 frontend/ 워크스페이스를 분리해 둔 레포 구조, 그리고 화면은 S1 API만 호출한다는 방침(계약 기반 병렬 개발)과 맞지 않다

## 전환 조건

스택 전환은 사실상 재작성이므로 측정 지표 기반 전환 조건을 두지 않는다. 대신 도메인 로직을 모듈 경계(0005) 안에 유지해 특정 프레임워크 결합을 낮추는 것을 방어선으로 삼는다.
