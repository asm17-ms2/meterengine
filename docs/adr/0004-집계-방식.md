# 0004. 집계 방식: 조회 시 raw 이벤트에서 계산

- 상태: 제안
- 결정일: 미정 (승인 시 기입)
- 관련 이슈: MS2-28

## 맥락

집계(MS2-39)를 조회/청구 시점에 raw 이벤트에서 계산할지, 이벤트 수신 시 사전 집계를 증분 유지할지 정해야 한다. MS2-39의 인수 조건에 "집계값은 raw 이벤트에서 재계산해 검증할 수 있다"가 포함되어 있고, raw 이벤트 불변성(정정은 이벤트로)은 확정된 불변 결정이다.

## 결정

사전 집계 테이블 없이, 조회와 청구 시점에 raw 이벤트에서 SQL로 집계(COUNT/SUM)한다. 결과 캐시도 S1에서는 도입하지 않는다.

지금 정하지 않는 것:

- 집계 반영 지연 목표치와 기간 경계(월 귀속) 규칙은 MS2-39 착수 시 확정한다
- 사전 집계 도입 시의 방식(증분 vs 배치 롤업)은 전환 조건 도달 시점에 결정한다

## 근거

- 진실의 출처가 raw 이벤트 하나로 유지된다. 집계값과 raw가 어긋날 가능성 자체가 없고, MS2-39의 재계산 검증 인수 조건과 그대로 정합한다
- 스프린트 1 Lago 분석에서 확인한 사실과 같은 방향이다: Lago는 청구 경로에 사전집계를 쓰지 않고 항상 raw를 스캔하며, 캐시는 표시용 근사치로만 쓴다. 청구는 정확해야 하기 때문이다
- 증분 사전 집계는 지연 도착 이벤트와 정정 이벤트가 올 때마다 재계산 경로가 필요해져, 정확성 검증 부담이 지금 규모의 이득보다 크다
- 미터 정의 변경(집계 대상 속성 변경 등)에도 재집계가 자유롭다

## 대안

- 증분 사전 집계 (이벤트 수신 시 집계값 갱신): 조회는 빨라지지만 진실의 출처가 둘이 되고, 지연/정정 이벤트 처리와 정합성 검증 코드가 S1 범위를 넘는다
- 배치 롤업 (시간/일 단위 사전 집계): 반영 지연이 생기고 기간 경계 처리가 복잡해진다. 트래픽이 커지면 유력한 후보지만 지금은 아니다
- 결과 캐시 (계산 결과를 캐싱): Lago 분석에서 이벤트 유입 시마다 무효화되어 활발한 고객일수록 hit률이 0에 수렴하는 것을 확인했다. 도입하더라도 무효화 전략을 따로 설계해야 한다

## 전환 조건

다음 중 하나가 관측되면 사전 집계(증분 또는 롤업) 도입을 검토한다. 도입하더라도 raw 재계산 검증 경로는 유지한다.

- 집계 조회 API p95 지연이 1초를 지속적으로 초과
- 인보이스 생성 시 집계 쿼리가 청구 배치 시간 창 안에 완료되지 못함
- 단일 고객의 청구 기간 내 이벤트가 수백만 건 규모에 도달
- 수치는 스파이크 없이 정한 제안치이므로 S1 구현에서 실측되면 갱신한다
