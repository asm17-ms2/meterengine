# 0003. 수집 경로: 동기 REST 직접 저장

- 상태: 승인
- 결정일: 2026-07-29
- 관련 이슈: MS2-28

## 맥락

이벤트 수집(MS2-38)을 동기 API가 요청 처리 중 직접 저장하는 구조로 갈지, 큐를 앞단에 둘지 정해야 한다. raw 이벤트는 청구의 근거라 유실이 곧 금액 오류이며, 멱등(transaction_id)과 불변성은 이미 확정된 불변 결정이다.

## 결정

동기 REST 단건 수집으로 시작한다. 요청 처리 중 PostgreSQL에 직접 저장하고, 성공 응답은 저장 완료(내구성 확보)를 의미한다. 멱등은 transaction_id 유니크 제약으로 DB에서 보장한다. 큐나 비동기 버퍼는 두지 않는다.

지금 정하지 않는 것:

- 배치 수집은 OpenAPI 명세에만 포함하고(MS2-27) 구현은 S1 범위 밖이다
- 큐 도입 시의 기술 선택(Kafka 등)은 전환 조건 도달 시점에 결정한다

## 근거

- 유실 지점이 최소다. 응답이 곧 저장 보장이므로 클라이언트가 재시도 판단을 스스로 할 수 있고, 중간 단계(큐, 컨슈머)의 장애 모드가 아예 없다
- 구성 요소가 API 서버와 DB뿐이라 3인 팀이 S1을 1주에 완주하는 데 가장 단순한 경로다
- Lago의 기본 경로도 동기 저장(요청 중 PostgreSQL 저장) + 후처리만 비동기 구조로, 이 규모에서 검증된 형태다
- 큐를 먼저 두면 at-least-once 재전달에 따른 중복 처리와 순서 문제를 지금 풀어야 하는데, 그 비용을 정당화할 트래픽이 아직 없다

## 대안

- 큐 선행 도입 (수집 API는 큐에 적재만, 컨슈머가 저장): 버스트 흡수와 처리량 확장은 얻지만, 응답이 저장 보장이 아니게 되어 유실 창이 생기고 운영 대상이 늘어난다
- 202 Accepted 비동기 수신 (서버 내부 버퍼): 큐의 단점만 갖고 내구성 장치도 없는 중간형이라 배제한다

## 전환 조건

다음 중 하나가 관측되면 큐 도입을 검토한다. 도입하더라도 수집 응답의 멱등 의미(같은 transaction_id 재전송 시 성공 응답)는 유지한다.

- 수집 API p95 지연이 200ms를 지속적으로 초과
- 버스트 유입 시 5xx나 타임아웃으로 인한 유실 관측
- 지속 유입이 1,000 events/s 초과 (0002의 조건과 공유)
- 수치는 스파이크 없이 정한 제안치이므로 S1 구현에서 실측되면 갱신한다
