# 0007. API JSON 필드명은 DTO에 @JsonProperty로 명시한다

- 상태: 제안
- 결정일: 2026-07-31
- 관련 이슈: MS2-38

## 맥락

`docs/api/openapi.yaml` 정본은 JSON 필드명을 snake_case로 규정한다. Java DTO의 필드는 camelCase이므로 그 사이에 변환이 필요하다.

첫 구현(MS2-38)에서 전역 설정 `spring.jackson.property-naming-strategy=SNAKE_CASE`로 변환했더니, 실제 응답은 snake_case로 나가는데 springdoc이 만든 구현 스냅샷(`docs/api/generated/openapi.yaml`)은 camelCase로 생성됐다.

원인은 Jackson 스택이 둘이라는 데 있다. Spring Boot 4의 런타임 직렬화는 Jackson 3(`tools.jackson`)가 하고, springdoc 3.0.3이 쓰는 swagger-core 2.2.47은 Jackson 2(`com.fasterxml.jackson`)로 클래스를 읽는다. 전역 설정은 Jackson 3 쪽이라 문서 생성기에 닿지 않는다. swagger-core는 아직 Jackson 3를 지원하지 않으므로 이 이중 구조 자체는 당분간 바뀌지 않는다.

MS2-31에서 생성 스냅샷을 레포에 커밋하는 계약을 만들었기 때문에(PR diff에 API 표면 변화를 드러내는 것이 목적), 스냅샷이 실제와 다르면 그 장치가 틀린 정보를 준다.

## 결정

외부 JSON에 노출되는 DTO 필드는 `@JsonProperty("snake_case_이름")`으로 외부 이름을 명시한다. 전역 네이밍 전략 설정은 쓰지 않는다.

- 대상은 요청/응답 DTO다. 직렬화되지 않는 내부 도메인 타입(`UsageEvent` 등)은 해당 없다
- 한 단어 필드(`code`, `properties`, `unresolved`)는 변환이 없으므로 붙이지 않는다
- 규약 위반은 `OpenApiNamingConventionTest`가 막는다. springdoc 생성 문서의 스키마 프로퍼티와 파라미터 이름에 대문자가 있으면 실패한다

## 근거

- `@JsonProperty`가 속한 `jackson-annotations`는 Jackson 3와 swagger-core(Jackson 2)가 공유한다. 런타임 직렬화와 문서 생성이 같은 애너테이션 하나를 읽으므로 이름이 어긋날 구조적 여지가 없어진다. 설정으로 양쪽을 맞추는 대신 이름을 코드에 고정하는 방식이다
- 필드 리네임이 외부 계약을 깨지 않는다. 전역 전략에서는 `occurredAt`을 다른 이름으로 바꾸는 순간 API가 조용히 바뀐다. 도입사가 붙는 고객 대면 표면에서 이 위험은 크다
- 계약이 국소적이다. DTO 파일만 열면 외부 이름을 알 수 있고 `transaction_id`로 grep하면 정의가 잡힌다
- 프레임워크가 내보내는 JSON에는 영향을 주지 않는다. 전역 전략은 우리가 작성하지 않은 응답까지 케이스를 바꾼다

비용은 두 단어 이상인 필드마다 애너테이션 한 줄이라는 점이다. 이 부담은 검사 테스트가 CI 실패로 드러내므로 사람의 기억에 의존하지 않는다.

## 대안

- **전역 SNAKE_CASE + `ModelResolver` 빈**: Jackson 2 ObjectMapper에 SNAKE_CASE를 걸어 `ModelResolver` 빈으로 등록하면 springdoc이 그 설정을 읽는다. 실제로 시험해 동작을 확인했다(빈 약 10줄로 전 필드가 snake_case로 생성됨). DTO에 애너테이션이 필요 없다는 점이 장점이다. 선택하지 않은 이유는 세 가지다. 같은 규약을 위한 설정이 런타임용과 문서용 두 벌이 된다. swagger-core가 Jackson 3를 지원하면 지워야 하는 임시 코드다. 필드 리네임이 외부 계약을 바꾸는 위험은 그대로 남는다
- **전역 SNAKE_CASE만**: 지금 상태다. 스냅샷이 camelCase로 남아 MS2-31이 만든 장치가 틀린 표면을 커밋한다
- **DTO에 `@JsonNaming(SnakeCaseStrategy)`**: 표면별로 케이스를 나눌 수 있다. 그러나 이 애너테이션은 Jackson 3의 `tools.jackson.databind.annotation` 소속이라 swagger-core(Jackson 2)가 읽지 못한다. 문서 불일치가 그대로 남는다

## 전환 조건

- swagger-core가 Jackson 3를 지원하면 전역 설정 한 줄로 돌아갈 수 있다. 그 시점에 DTO 수와 애너테이션 소음을 보고 재검토한다
- DTO가 늘어 애너테이션 관리 부담이 체감되면 재검토한다. 그때는 위 `ModelResolver` 대안이 후보다
- 콘솔 내부 API를 camelCase로 두기로 하면 이 ADR의 적용 범위를 표면별로 나눠 다시 쓴다
