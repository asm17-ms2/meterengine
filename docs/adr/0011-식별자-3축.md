# 0011. 식별자 체계: 3축 분리와 external_id 단일 API 표면

- 상태: 제안
- 결정일: 2026-07-29 (데일리 비준, PR 머지 시 승인으로 변경)
- 관련 이슈: MS2-26

## 맥락

엔티티를 무엇으로 식별하고 참조하는지 정해야 한다. 식별자는 이벤트 계약과 FK에 박히므로 나중에 바꾸면 전 데이터와 전 API가 흔들린다. "ID"로 뭉뚱그리지 않고 용도별로 축을 나누는 것이 핵심이다.

## 결정

식별자를 3축으로 분리한다.

- 내부 PK(UUID): 테이블 간 FK와 내부 참조 전용. 불변이며 외부에 노출하지 않는다
- external_id: 도입사 시스템과의 통합용(고객). (도입사, external_id) 유니크
- code: 카탈로그 참조용(미터). (도입사, code) 유니크. 이벤트가 code를 실어 미터를 지목한다

부속 결정:

- API 표면도 external_id 단일 축이다. 고객 조회 경로는 `/customers/{external_id}/...` 형태만 쓰고 내부 UUID를 노출하지 않는다. cus_ 접두사 공개 ID는 도입하지 않는다 (MS2-27 D-5, 2026-07-29 합의)
- 정의성 엔티티(고객, 미터)는 soft delete(deleted_at) 후 이름 재사용을 허용한다. 유니크는 살아있는 행끼리만 적용한다(부분 유니크 인덱스)

## 근거

- 내부 PK를 외부에 노출하면 도입사가 우리 내부 구조에 결합되고, 도입사 입장에선 자기 시스템의 ID로 부를 수 없어 통합 비용이 생긴다
- 재사용 허용이 안전한 이유는 0007이다. 이벤트가 수신 시점 UUID에 고정되므로 이름이 재사용돼도 과거 이벤트의 귀속은 변하지 않는다. 0007이 뒤집히면 이 재사용 허용도 재검토해야 한다 (두 결정은 묶여 있다)
- S1 이벤트 계약 필드는 transaction_id, code, external_customer_id, properties, occurred_at이다 (구독 부재로 v0 계약의 external_subscription_id 자리를 external_customer_id가 대신한다). 요청 스키마 상세는 MS2-27 소관이다

## 대안

- 공개 ID 접두사 도입 (cus_xxx, Stripe 방식): 도입사가 우리가 발급한 두 번째 ID를 자기 시스템에 저장해야 해서 통합 비용이 늘어난다. S1 규모에서 얻는 것이 없어 미도입으로 합의했다
- 단일 ID 축 (내부 PK 노출): 내부 구조 결합과 재사용 문제를 동시에 일으켜 배제

## 전환 조건

- 외부 노출용 불투명 ID가 필요한 요구(웹훅 페이로드 등)가 생기면 공개 ID 도입을 그 시점에 재검토한다
