# 문서 관리 규칙

버전 v1.0 | 2026-08-01

MeterEngine의 문서를 어디에 두고 어디서 논의할지 정한다. 새 문서를 만들기 전에 이 문서를 먼저 본다.

이 문서 자체는 개발 규약이다 (아래 Q4). 브랜치와 PR 규약은 `CONTRIBUTING.md`에 있다.

---

## 1. 판별 순서

위에서부터 순서대로 물어보고, 처음 걸리는 곳에서 멈춘다.

### Q1. 되돌리기 비싼 결정인가

다음 중 하나에 해당하면 **ADR**이다.

- 과거 데이터가 새 규칙과 불일치하게 된다 (예: 유니크 인덱스 구성, 시간 의미론, 반올림 규칙)
- 외부에 한 약속이 바뀐다 (예: 보존 기간, 지연 이벤트 처리 정책, SLA)

판별 보조 질문: 6개월 뒤 이 코드를 여는 사람이 "왜 이렇게 했지"라고 물을 것 같은가.

**Q1만 비배타적이다.** ADR을 쓰고, 결정한 값을 코드가 참조하면 SPEC에도 행을 추가한다 (5절 참조). 나머지 질문은 하나만 고른다.

### Q2. 화면 동작을 서술하는가

사용자가 화면에서 무엇을 보고 무엇을 하는지 정하는 문서면 **기능 명세**다. Jira 스토리의 인수 조건으로 쓰고 별도 문서를 만들지 않는다.

### Q3. 코드가 구현하는가

숫자나 규칙을 코드가 참조하고, 어기면 빌드나 테스트가 깨지면 여기서 갈린다.

```
고객이 호출하는 API 표면인가   ->  docs/api/
그 외 값과 규칙                ->  docs/spec/
```

보조 판별: 에러 코드를 하나 발급해야 하면 이 갈래다. 그 코드가 API 응답에 나가면 `docs/api/`, 화면에만 있으면 Q2로 돌아가 기능 명세다.

### Q4. 사람이 지키는가

절차나 규범이면 셋 중 하나다.

- **정책**: 바꿀 때 합의가 필요하다
- **팀 협약**: 그냥 정하면 된다
- **개발 규약**: 개발 작업 절차 자체다 (이 문서, `CONTRIBUTING.md`)

### Q5. 어느 저장소에 둘 것인가

정책과 협약 중 **코드 작업 중에 열어보는 것**은 레포에 둔다. 그렇지 않으면 Notion. 개발 규약은 항상 레포다.

## 2. 위치

| 문서 종류 | 위치 | 예 |
|---|---|---|
| 정책 | Notion 정책 DB | 데이터 반환 절차, 문서 외부 공개 기준 |
| 팀 협약 | Notion 팀 협약 페이지 | 스프린트 길이, 데일리 시각, Jira 사용 규칙 |
| 개발 규약 (브랜치, PR) | `CONTRIBUTING.md` | 브랜치명, 머지 방식, 리뷰 규칙 |
| 개발 규약 (문서 분류와 위치) | 이 문서 | |
| 시스템 사양 | `docs/spec/` | 멱등성, 시간 의미론, 보존 기간, 에러 카탈로그 |
| 결정 기록 | `docs/adr/` | 저장소 선택, 수집 경로, 집계 방식 |
| 기능 명세 | Jira 스토리 인수 조건 | 화면 동작, 표시 항목, 빈 상태 처리 |
| 고객 대면 API 계약 | `docs/api/openapi.yaml` | 엔드포인트, 요청 응답 스키마, 에러 응답 |
| 내부 콘솔 API | `docs/api/` 수기로 시작, 구현 완료 후 생성물로 승격 | MS2-46 이후 적용. 상세는 `docs/api/README.md` |
| 스키마와 ERD | `docs/erd/` | tbls 생성물(전환 중). 직접 편집하지 않는다 |
| 아키텍처 다이어그램 | `docs/architecture/` (신설 예정) | 컴포넌트 구성, 데이터 흐름 |
| 회의록 | Notion 회의록 DB | |

`docs/`가 기술 문서의 정본이다. 같은 내용을 Notion에 복제하지 않는다.

스키마 변경의 입구는 Flyway 마이그레이션이다. ERD 문서를 고쳐서 스키마를 바꾸는 경로는 없다. 제약을 새로 정할 때 그 근거는 SPEC이나 ADR에 쓴다 (Q1, Q3).

## 3. 토론 장소

| 문서 종류 | 결정하는 곳 | PR의 역할 |
|---|---|---|
| 정책 | Notion 제자리에서 인라인 코멘트 | 해당 없음 |
| 팀 협약 | 회고나 대화 | 해당 없음 |
| SPEC | PR 코멘트 | 심의 |
| ADR | PR (제안 -> 승인) | 심의와 기록 |
| 기능 명세 | Jira 이슈 코멘트 | 해당 없음 |

### ADR을 PR에서 결정하는 이유

```
제안 상태로 ADR 작성 후 PR
  -> 나머지 둘이 검토
  -> 승인 또는 기각으로 상태 변경
  -> 머지
```

기각 기록 때문이다. Slack이나 통화에서 결론을 내고 오면, 채택된 안만 ADR로 올라오고 기각된 안은 아무 데도 남지 않는다. 반년 뒤 같은 논의가 처음부터 재발한다.

기각과 철회의 구분, 무엇을 남기고 무엇을 남기지 않는지, 번호 처리는 `docs/adr/README.md`에 있다. 형식은 `docs/adr/template.md`를 따른다.

### Slack에서 결정할 때

스레드 마지막에 결론 한 줄을 남긴다. 남기지 않으면 세 사람이 각자 다른 것을 합의했다고 믿는 상태가 된다.

```
결론: 멱등키 유일성 범위는 (organization_id, transaction_id).
구독별은 late binding과 충돌해서 기각. ADR 작성은 성종.
```

Slack 링크는 보조로만 건다. 무료 플랜은 메시지 보존 기간 제한이 있어 몇 달 뒤 링크가 죽는다. 결론과 이유는 ADR 본문에 다시 쓴다. **모든 문서는 링크를 열지 않고도 혼자서 읽혀야 한다.**

### 제안 문서

새 정책을 처음 만들거나 전면 개정할 때, 전제부터 갈리는 큰 결정에는 제안 상태 ADR을 쓴다. 멘토 리뷰가 필요한 문서도 마찬가지다. 레포가 public이므로 조직 밖에서도 PR에 코멘트를 달 수 있다.

별도 문서 도구를 쓰지 않는다. 외부 도구는 기각을 상태로 기록할 수 없어 재발 방지가 안 된다.

## 4. 문서별 작성 규칙

ADR은 `docs/adr/README.md`와 `docs/adr/template.md`를 따른다. 아래는 나머지 셋이다.

### 정책 (Notion)

정책 DB의 속성으로 메타 정보를 관리한다.

| 속성 | 타입 |
|---|---|
| 버전 | 텍스트 (`v1.3`) |
| 상태 | 상태 (초안, 검토중, 유효, 폐기) |
| 최종 개정일 | 날짜. 손으로 갱신하며, 의미 있는 개정만 반영한다 |

자동 편집 시각은 속성으로 두지 않는다. 오타 수정으로도 갱신되어 "정책이 실제로 언제 바뀌었나"에 답하지 못한다.

본문 하단에 변경 이력 표를 둔다. Notion 무료 플랜의 페이지 기록은 7일까지만 열람되므로 이 표가 실질적인 이력이다.

메이저 버전을 올릴 때만 페이지를 복제해 `[Archive] 정책명 v1.x`로 보관한다. 폐기된 정책은 삭제하지 않고 상태만 폐기로 바꾼다.

#### 값을 인용할 때

값의 정본은 `docs/spec/`이다. 정책 문서가 값을 인용해야 하면 정본을 병기한다.

```
보존 5년(정본 docs/spec/retention.md)
```

**값 없이 쓸 수 있으면 쓰지 않는다.** 데이터 반환 절차에 실제로 필요한 건 "법정 보존 의무가 남은 데이터를 제외하고 반환한다"이지 숫자가 아니다. 숫자를 넣는 순간 SPEC과 어긋날 자리가 하나 생긴다.

### SPEC

값과 경계 조건을 표로 쓴다. 근거 열은 "왜 골랐나"가 아니라 **"바꿔도 되나"**에 답한다.

아래는 형식 예시다.

```markdown
# 멱등성

## 규칙

| 항목 | 값 | 근거 / 변경 가능성 |
|---|---|---|
| 유일성 범위 | (organization_id, transaction_id) | 결정 1. 변경 시 인덱스 재구성과 마이그레이션 필요 |
| 유일성 기간 | 무기한. 기간 윈도우 없음 | 결정 1. 축소하면 과거 이벤트가 재수용된다 |
| 중복 응답 | 최초 201, 재전송 200 + 기존 결과 | MS2-27 공통 규약 |

## 경계
- 배치 내 중복은 첫 건만 수용한다
- 제어면 멱등키는 최소 24시간 보존하며, 만료 후 같은 키는 새 요청으로 처리된다

## 관련
- ADR-00NN 멱등성 게이트 위치
- 구현 `IdempotencyGuard` / 테스트 `IdempotencyGuardTest`
```

근거가 세 줄을 넘어가면 ADR로 올리라는 신호다.

관련 섹션의 구현 및 테스트 링크는 생략하지 않는다. 사양과 코드가 한쪽만 바뀌는 사고를 막는 장치다.

**역방향 링크.** 값이 코드에 들어가면 상수 선언부 주석에 SPEC 경로와 항목을 적는다. 값을 고치러 오는 사람은 대개 코드에서 출발하며, SPEC에서 코드로 가는 링크만 있으면 그 사람은 SPEC의 존재를 모른다. 테스트에는 따로 적지 않는다. 테스트가 그 상수를 참조하기 때문이다. 값이 상수 없이 리터럴로 흩어져 있으면 링크를 걸 자리가 없다는 뜻이고, 그 자체가 먼저 고칠 문제다.

### 기능 명세

Jira 스토리의 인수 조건으로 쓴다. 별도 문서를 만들지 않는다.

```
Given 콘솔에 로그인한 사용자가
When 고객 상세 화면에 진입하면
Then 이번 청구 주기의 미터별 누적 사용량을 본다
And 최근 인보이스 5건을 상태와 함께 본다
And 사용량이 0이면 빈 상태 안내를 본다
```

화면 동작은 구현 이후 코드와 테스트가 진실이다. `docs/`에 남기면 UI 변경을 따라가지 못해 썩는다.

와이어프레임이나 상태 전이도가 필요할 만큼 복잡하면 Notion에 한 장 쓰고 Jira에서 링크한다. 구현 후에는 최신화하지 않는다.

## 5. 하나의 사안이 여러 문서를 만드는 경우

보존 기간을 예로 든다. ADR 번호는 예시다.

| 문서 | 담는 것 |
|---|---|
| `docs/adr/00NN-보존-기간.md` | 왜 5년인가. 세법 5년, 상법 10년, 전자금융거래법의 중첩 검토와 기각한 대안 |
| `docs/spec/retention.md` | 보존 5년, `retention_until` 필드, 아카이브 시점, 테넌트 오버라이드 범위 |
| Notion 정책 | 계약 종료 시 데이터 반환 절차. 접수 담당, 처리 기한, 파기 확인서 |

셋의 역할은 이렇게 고정한다.

- `docs/spec/` 값이 무엇인가
- `docs/adr/` 왜 그 값인가
- Notion 사람이 무엇을 하는가

셋을 하나로 합치려 하면 반드시 하나가 썩는다. 5년이라는 숫자만 ADR과 SPEC에 공통으로 나오는데, SPEC은 "5년이다", ADR은 "왜 5년인가"라 역할이 다르다.

**인간 절차가 없는 건은 Notion 칸이 비는 것이 정상이다.** 절사 방식이 그렇다. 값은 SPEC, 근거는 ADR로 끝나고 사람이 수행할 절차가 없다. 빈 칸을 채우려고 정책 문서를 만들지 않는다.

## 6. 자주 나는 실수

| 실수 | 교정 |
|---|---|
| SPEC에 근거를 길게 씀 | 세 줄 넘으면 ADR로 분리 |
| 같은 값을 SPEC과 Notion에 둘 다 씀 | 값은 SPEC 하나. 정책은 정본을 병기해 인용 |
| 승인된 ADR을 고침 | 새 번호를 따고 이전 것은 대체됨으로 |
| 화면 명세를 `docs/`에 둠 | Jira 인수 조건으로 |
| 정책 DB에 협약을 넣음 | 자주 바뀌는 것은 협약 페이지로 |
| 링크만 남기고 결론을 안 씀 | 결론과 이유를 본문에 다시 씀 |
| ADR을 한꺼번에 여러 장 쓰려 함 | 하나씩. 되돌리기 비싼 순서로 |

## 이관 대기

SPEC 계층이 생기기 전에 다른 곳에 쌓인 값이다. 이관이 끝나면 해당 줄을 지운다.

| 대상 | 현재 위치 | 이관처 | Jira |
|---|---|---|---|
| 절사 방식과 단수 규칙 | Notion | `docs/spec/` | 미생성 |
| ERD 제약 근거, 의도된 제외 | `docs/erd/erd.md` | `docs/spec/`, `docs/adr/` | 미생성 |

두 번째 건은 tbls 전환 이후에 진행한다. 생성물이 대체하지 못하는 구간(제약 표의 근거 열, 의도된 제외, 스토리별 이관 항목)이 남아 있다.
