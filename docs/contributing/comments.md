# 주석과 javadoc

주석을 쓰지 않는다. javadoc도 주석이다. 코드만 읽어도 이해되게 쓰고, 코드가 맞게 도는지는 테스트로 관리한다. 예외는 아래 "한 줄 설명"뿐이다. 왜 이렇게 정했는지는 RFC-002에 있다.

주석을 쓰고 싶어지면 그 내용은 아래 중 한 곳으로 간다.

| 쓰고 싶은 것 | 가는 곳 |
| --- | --- |
| 방향, 그리고 검토했지만 고르지 않은 길 | `docs/rfcs/` |
| 정해진 값과 경계 조건, 그 값이 나온 근거 | `docs/policies/<도메인>.md`. 그 도메인의 정책 파일이 없으면 그 PR에서 만든다 |
| 깨지면 안 되는 전제 | 테스트. 고치면 실패하고 테스트 이름이 이유를 말한다 |
| 다른 정본에 이미 있는 것 | 지운다 |

커밋 본문은 행선지로 쓰지 않는다. blame이 설명 없는 기능 커밋이나 빈 줄 커밋을 가리켜 찾을 문구를 이미 아는 사람만 닿는다.

이름과 구조로 표현되지 않아 주석을 붙이고 싶어지면, 대개 이름이나 분리가 잘못된 것이다. 주석을 쓰는 대신 그쪽을 고친다. 구조로 강제해야 하는 규칙이 생기면 주석이 아니라 아키텍처 테스트나 CI 검사로 넣는다.

## 한 줄 설명

함수 바로 위에 그 함수가 무엇을 하는지 한 줄로 적을 수 있다. 필드나 상수 위에 같은 형식으로 붙는 줄도 같은 규칙을 받는다. 아래를 모두 지킨다.

- 한 문장이고 마침표가 하나다
- 무엇을 하는지만 적는다. 왜 그렇게 했는지는 적지 않는다. 그것은 RFC와 정책과 커밋 본문의 몫이다
- 옆의 목록이나 코드를 세어 개수를 적지 않는다
- 다른 파일의 주석을 가리키지 않는다
- 코드에 없는 사실을 주장하지 않는다. 실측값, 성능, 외부 시스템의 동작이 여기 든다

함수 본문 안에는 쓰지 않는다. 본문을 설명하고 싶으면 함수를 쪼갠다.

```
// 고객을 등록한다.
```

## 주석이 아닌 것

- **도구 지시문**: `@SuppressWarnings`, `// eslint-disable-next-line`처럼 도구가 읽는 것. 억제가 필요한 이유까지 덧붙이지는 않는다
- **`@Schema`, `@Operation`, `@Parameter`, `@ApiResponse`의 description**: API 계약이다. `backend/openapi.yaml`로 나가 프론트엔드와 외부가 읽는다. Jira 키를 넣지 않는다
- **파일을 눈으로 나누는 구분자**: `// --- 등록 ---`처럼 명사구 레이블 한 줄과 구분선. 테스트와 SQL에서 쓴다. 레이블이 문장이 되거나 파일 밖 이름을 담으면 주석이므로 위 규칙을 받는다

## 마이그레이션

마이그레이션 파일의 주석도 대상이다. `V__` 파일은 체크섬이 내용 전체로 계산되어 주석만 고쳐도 이미 적용된 DB와 어긋나 기동이 실패한다. 고칠 때는 배포 DB와 각자 로컬 볼륨의 체크섬을 함께 맞춘다. CI는 매번 빈 DB라 이 실패를 잡지 못한다.

## 적용 시점

규칙 이전에 쌓인 주석은 전수 정리한다. 정리 PR은 대상 코드(백엔드 도메인 패키지, 도메인 없는 최상위, 프론트엔드, 마이그레이션)로 가르고, 그 도메인의 주석 삭제와 문서 추가를 한 PR에 담는다. 지우는 심볼을 가리키는 다른 파일의 문장도 같은 PR에서 처리한다. 정리를 마친 파일에는 한 줄 설명만 남고, 지우면서 새로 붙이지는 않는다.

**주변 코드에 주석이 많아도 그것을 근거로 삼지 않는다.** 기존 파일의 주석 밀도는 규칙 이전 상태이지 따라야 할 본보기가 아니다.
