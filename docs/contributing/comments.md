# 주석과 javadoc

주석을 쓰지 않는다. javadoc도 주석이다. 코드만 읽어도 이해되게 쓰고, 코드가 맞게 도는지는 테스트로 관리한다.

주석을 쓰고 싶어지면 그 내용은 아래 중 한 곳으로 간다.

| 쓰고 싶은 것 | 가는 곳 |
| --- | --- |
| 왜 이렇게 설계했는지, 무엇을 검토하고 무엇을 택했는지 | `docs/rfcs/`와 `docs/policies/`. 결정과 정책의 정본이다 |
| 이 변경을 왜 했는지 | 커밋 메시지와 PR 본문. blame으로 찾아진다 |
| 순진하게 고치면 깨진다, 이 제약을 지켜야 한다 | 테스트. 고치면 실패하고 테스트 이름이 이유를 말한다 |

주석은 틀려도 아무것도 실패하지 않는다. 그래서 시간이 지나면 코드와 어긋난 채 남아 읽는 사람을 잘못된 곳으로 보낸다. 구조로 강제해야 하는 규칙이 생기면 주석이 아니라 아키텍처 테스트나 CI 검사로 넣는다.

이름과 구조로 표현되지 않아 주석을 붙이고 싶어지면, 대개 이름이나 분리가 잘못된 것이다. 주석을 쓰는 대신 그쪽을 고친다.

## 주석이 아닌 것

아래는 이 규칙의 대상이 아니다.

- **도구 지시문**: `@SuppressWarnings`, `// eslint-disable-next-line`처럼 도구가 읽는 것. 설명이 아니라 지시문이다. 억제가 필요한 이유까지 덧붙이지는 않는다
- **`@Schema`, `@Operation`의 description**: 주석이 아니라 API 계약이다. `backend/openapi.yaml`로 나가 프론트엔드와 외부가 읽는다

## 적용 시점

지금부터 새로 쓰거나 고치는 코드에 적용한다. 기존 주석과 javadoc은 소급해서 지우지 않는다. 작업 중에 편집한 파일에 주석이나 javadoc이 있으면 그 파일의 주석과 javadoc 정리를 맡되, 하던 PR에 섞지 않고 그 정리만 하는 PR을 따로 연다. 섞으면 리뷰어가 기능 변경과 주석 삭제를 한 diff에서 갈라 읽어야 한다.

**주변 코드에 주석이 많아도 그것을 근거로 삼지 않는다.** 기존 파일의 주석 밀도는 규칙 이전 상태이지 따라야 할 본보기가 아니다.
