# PR 크기, 쪼개기, 스택

브랜치, 커밋, 승인 같은 확정된 규칙은 CONTRIBUTING.md에 있다. 이 파일은 PR을 얼마나 작게, 어떻게 나누고, 나눈 조각을 어떻게 쌓아 머지하는지를 정한다.

## PR 크기와 쪼개기

리뷰가 읽기 편한 단위가 기준이다. 줄 수는 그 단위를 지키게 하는 상한이지 목표가 아니다.

- **하한은 없다.** 1줄 PR도 그게 읽기 편하면 그대로 낸다. 함수명 변경처럼 기계적인 작업도 단일 기능이 아니면 한꺼번에 바꾸지 않고 나눈다
- **상한은 300줄이다.** 추가된 줄(+)을 테스트까지 포함해 센다. 빼고 세는 것은 아래뿐이다
  - 생성물: `backend/openapi.yaml`, 잠금 파일
  - 삭제된 줄
- 삭제를 빼고 세므로 순수 삭제는 사실상 상한을 받지 않는다. 죽은 코드를 지우는 것을 상한으로 막지 않으려는 것이다. 대신 지우는 근거는 PR 본문에 적는다
- 같은 파일을 지우고 다시 쓰는 재작성은 숫자보다 리뷰가 무겁다. 삭제가 추가보다 크면 리뷰어가 지운 것과 새로 쓴 것을 둘 다 읽어야 하므로, 그런 PR은 상한과 별개로 더 잘게 나눈다
- 생성물은 줄 수에서만 빼는 것이고, diff에 올라왔는지는 리뷰에서 본다. CI가 검사하지 않아 빠뜨려도 아무것도 실패하지 않는다 (CLAUDE.md "OpenAPI 생성물")
- **테스트는 기능과 같은 PR에 둔다.** 다음 PR로 미루지 않는다. 테스트 없는 기능 PR은 리뷰어가 맞는지 판단할 근거가 없고, CI도 "기존 테스트가 안 깨졌다"만 확인하게 된다. 테스트만 있는 PR은 이미 머지된 코드의 테스트를 보강할 때로 한정한다
- **초과**: `backend/`, `.github/`, `deploy/`는 초과하지 않는다. `frontend/`, `demo/`는 작성자 판단으로 넘길 수 있고 PR 본문에 이유를 적는다
- **PR 하나당 서브태스크 하나**를 목표로 한다. 맡은 서브태스크가 300줄을 넘길 것 같으면 티켓부터 쪼갠다. 티켓을 새로 만들 필요가 없는 자잘한 작업은 아래 "티켓 없이 가는 작업"을 따른다

### 티켓 없이 가는 작업

오타, 죽은 링크, 포맷, 액션이나 의존성 버전 올리기처럼 자잘한 작업은 Jira 티켓을 만들지 않고 그냥 PR로 올린다. 티켓을 만들고 상태를 옮기는 비용이 작업 자체보다 큰 경우다.

가르는 기준은 나중에 Jira에서 되짚을 일이 있는지다.

- **티켓을 만든다**: 동작이나 정책이 바뀌는 것, 왜 했는지 diff 밖에 설명이 필요한 것, 스프린트 범위나 진행 상황으로 추적해야 하는 것
- **그냥 올린다**: 결과가 diff에 다 드러나고, 무엇을 왜 했는지 커밋 메시지 한 줄로 끝나는 것

애매하면 티켓을 만든다. 티켓 없이 올릴 때도 왜 했는지는 PR 본문에 적는다.

티켓이 없으면 브랜치명에서 이슈 키를 뺀다. `docs/fix-readme-link`처럼 `<type>/<설명>`으로만 쓴다.

### 쪼개는 축

층은 최소 단위가 아니다. 컨트롤러 하나가 엔드포인트 여러 개이고, 통합테스트 파일 하나가 서로 독립된 `@Test` 여러 개다. 위에서부터 적용한다.

1. **동작별** - 엔드포인트나 화면 동작이 여럿이면 그걸로 자른다. 기본 축이다. 각 PR은 동작 하나 + 그 동작이 처음 쓰는 DTO/예외 + 그 동작의 테스트를 갖는다
2. **층별** - 동작이 하나뿐인데 크면 모델 / 서비스 / 컨트롤러로 자른다. 새 도메인 모델을 들여올 때가 이 경우다
3. **경로별** - 그래도 넘으면 성공 경로 / 검증 실패 / 동시성으로 자른다. 통합테스트가 마지막 조각에 몰릴 때 쓴다

**바닥은 관찰 가능한 동작 하나다.** 그 아래로는 쪼개지 않는다. DTO만 있는 PR이나 검증 로직만 떼낸 PR은 호출되는 곳이 없어 리뷰어가 모양이 맞는지 판단할 수 없다.

고객 CRUD(전체 1593줄)를 동작별로 자르면 아래처럼 된다. 테스트를 포함한 값이다.

| 조각 | 줄 |
| --- | --- |
| 엔티티 + 리포지토리 + 스키마 테스트 | 79 |
| GET 목록 + 응답 DTO + 테스트 | 200 |
| POST 등록 + 요청 DTO + 테스트 | 200 |
| PUT 수정 + 테스트 | 180 |
| DELETE + 예외 + 동시성 테스트 | 300 |

한 슬라이스가 여러 조각으로 나뉘면 스택 PR로 쌓는다. 머지 순서는 아래 "스택 PR"에 있다.

## 스택 PR

**독립 PR이 먼저다.** 따로 머지돼도 상관없는 작업이면 각각 main에서 브랜치를 따 독립 PR로 낸다.

스택은 아래 중 하나일 때 쓴다.

- 조각이 따로 머지되면 반만 동작하는 상태가 main에 남는다. 한 덩어리로 갔어야 할 작업이 300줄 상한 때문에 쪼개진 경우가 대부분이다
- 뒤 PR이 앞 PR 없이는 성립하지 않는다. 줄 수와 무관하다
- 한 기능을 순서대로 읽어야 이해된다. 파일 이동과 내용 변경을 나눈 경우처럼, 각 조각은 따로 봐도 말이 되지만 왜 그렇게 했는지는 순서로만 드러난다

세 번째는 "그게 편해서"로 넓어지기 쉽다. 순서를 바꿔 읽어도 이해되면 독립 PR이다.

스택으로 갈 때는 main이 아니라 선행 브랜치 위에 쌓는다. 몇 단이든 쌓아도 된다.

어느 PR에서 머지하든 그 아래 머지되지 않은 PR이 함께 들어간다. 최상단에서 머지하면 슬라이스 전체가 한 번에 올라가고, 하단만 승인됐으면 그것만 단독으로 머지할 수도 있다. 남은 자식들은 base가 자동으로 다시 잡힌다. 스택 안의 각 PR에도 "본인 외 1명 승인"이 그대로 걸리므로, 잘게 쪼갠다고 리뷰가 헐거워지지는 않는다.

### 머지 순서

**호출 경로가 열리는지로 가른다.**

- **내부 구조만 늘리는 조각** (엔티티, 리포지토리, 내부 서비스): 담당자 재량이다. 승인되는 대로 하나씩 머지하든, 몇 개씩 묶든, 최상단에서 한 번에 밀든 상관없다. 아무도 호출하지 않는 코드라 밖에서 보이는 것이 달라지지 않는다
- **컨트롤러나 화면이 들어가는 조각**: 가급적 한 번에 머지한다. 머지되는 순간 밖에서 부를 수 있는데, 뒤에 올 검증이나 오류 처리가 아직 없으면 반만 동작하는 API가 노출된다

어느 쪽이든 각 PR은 자기 브랜치에서 필수 체크를 통과해야 머지되므로 "main은 항상 빌드/테스트가 통과하는 상태"는 유지된다.

**GitHub 네이티브 스택 PR 기능만 쓴다. 수동 git으로 스택을 만들거나 정리하지 않는다.** 2026-08 기준 public preview라 널리 알려진 기능이 아니어서, 익숙한 수동 rebase 절차로 되돌아가기 쉽다. 그러면 스택으로 인식되지 않는 PR이 생기거나 히스토리가 어긋난다.

| 하려는 일 | 쓰지 않는다 | 대신 쓴다 |
| --- | --- | --- |
| 선행 브랜치 위에 새 작업 시작 | `git checkout -b`로 그냥 따기 | `gh stack init` |
| 이미 있는 스택에 합류 | 브랜치 이름으로 checkout | `gh stack checkout <PR번호>` |
| PR 올리기 | `gh pr create --base <부모브랜치>` (diff만 맞고 스택으로 인식되지 않는다) | `gh stack submit` |
| 부모가 갱신됐을 때 맞추기 | `git rebase --onto`, `git rebase --update-refs`, `git rebase -i` | `gh stack sync` |
| 부모가 머지된 뒤 | 손으로 base 바꾸기, 손으로 rebase | 아무것도 하지 않는다. GitHub가 base를 다시 잡는다. 로컬만 `gh stack sync` |
| 스택 브랜치 push | `git push --force` | `gh stack submit` |
| 구조 확인 | `git log --graph`로 추정 | `gh stack view` |
| 이미 올린 PR을 스택으로 묶기 | base만 바꾸기 | `gh stack link` 또는 웹에서 묶기 |

확장이 없으면 `gh extension install github/gh-stack`으로 설치한다. 설치나 명령이 실패하면 수동 git으로 우회하지 말고 멈추고 물어본다. 모르는 하위 명령은 추측하지 말고 `gh stack --help`나 아래 문서를 본다.

- 개념과 머지 동작: https://github.github.com/gh-stack/introduction/overview/
- CLI 레퍼런스: https://github.github.com/gh-stack/reference/cli/
- GitHub 공식 문서: https://docs.github.com/ko/pull-requests/get-started/about-stacked-prs

승인되지 않은 부모를 끌고 들어가는 자식 머지는 요청하지 않는다. 머지는 웹에서 하든 `gh stack merge`로 하든 상관없다. main 룰셋에 bypass가 전부 꺼져 있어 어느 경로로 머지해도 승인과 필수 체크가 똑같이 강제된다.

머지 큐를 켜면 스택의 원자성이 깨진다. 큐 모드는 각 PR을 아래에서부터 개별로 평가해서 main이 중간 상태를 실제로 거친다. 지금은 쓰지 않으며, 도입을 논의할 때 이 항목을 같이 본다.
