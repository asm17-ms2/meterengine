# 브랜치, 커밋, 머지

- main에는 직접 push할 수 없다. 모든 변경은 브랜치를 만들어 PR로 올린다.
- work/는 개인 작업 공간이라 PR 대상이 아니다.

## 브랜치

- 이름은 `<type>/MS2-<이슈번호>-<설명>`. 예: `docs/MS2-31-branch-strategy`.
  - type은 feat, fix, docs, refactor, test, ci, chore.
  - 이슈 키로 Jira가 브랜치와 PR을 이슈에 자동 연결한다.
  - 티켓 없이 가는 작업은 키를 빼고 `<type>/<설명>`. 기준은 `pull-request.md` "티켓 없이 가는 작업".
- 머지된 브랜치는 삭제된다. 이어지는 작업은 main에서 새 브랜치를 딴다.
  - 머지되지 않은 선행 작업에 의존하면 그 브랜치 위에 쌓는다. `pull-request.md` "스택 PR".
  - 로컬 브랜치는 각자 `git fetch --prune`으로 정리한다.

## 커밋 메시지

- 제목은 `<type>: <요약> (MS2-xxx)`. 티켓이 없으면 `(MS2-xxx)`를 뺀다.
  - RFC PR은 `RFC-NNN: 제목`. 결정 내용을 바꾸지 않는 정정은 일반 양식.
- 본문은 왜 / 변경 사항 / 결과와 검증 절로 쓴다.
  - 사소한 변경(오타, 링크, 버전 올리기)은 제목 한 줄로 끝내도 된다.
  - 절 제목에 `#`을 쓰지 않는다. git이 주석으로 지운다.
- 왜 그렇게 정했는지는 커밋 본문이 정본이다. 규칙 파일과 정책 파일에는 적지 않는다.
- PR 하나에 커밋 하나를 최대한 유지한다. 나눠야 하면 PR 본문에 이유를 적는다.

## 머지 방식

- squash merge. main 룰셋이 강제한다.
- 고정 브랜치(develop, staging)가 생기면 develop 룰셋은 squash만, main 룰셋은 merge commit만 허용으로 바꾼다. 시점은 릴리스 규칙 논의와 함께 정한다.

## 릴리스와 태그

- 버전 태그는 두지 않는다. 배포 단위는 커밋이고 이름은 git SHA다(ECR 이미지 태그가 SHA다).
  - 롤백은 이전 SHA로 다시 배포한다.
  - 외부에 버전 번호를 알려야 하는 일이 생기면 그때 다시 논의한다.
