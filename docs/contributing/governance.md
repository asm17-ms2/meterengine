# 결정과 규칙의 위치와 개정

## RFC

### 규칙

- 무엇: 되돌리면 외부 계약, 쌓인 데이터, 그 위에 선 코드 전체가 같이 움직이는 방향 결정과 그 이유.
- 어디: `docs/rfcs/`.
- 결정 하나에 한 장.
- 머지된 뒤에는 본문을 고치지 않는다. 오탈자와 죽은 링크는 고친다.
- 결정을 바꾸면 새 RFC를 쓴다. 옛 RFC는 `status: superseded`와 `superseded-by`만 적는다.

### 근거

- 머지 직후 팀이 그 결정대로 코드를 쓰고 다른 PR이 그 RFC를 가리키기 시작한다.
- 본문을 고치면 "그때 왜 그랬나"가 사라지고, 뒤집은 이유가 한 장으로 남지 않는다.
- 구현 진행은 Jira에 있어 RFC 안에 살아 있을 것이 없다.

### 검토한 대안

- KEP식. 결정 문서를 살려 두고 구현이 끝날 때까지 전원 재승인으로 고친다: 구현 진행을 Jira에 두므로 문서 안에 살아 있을 것이 없다. 결정 하나에 한 장이라 고치는 대신 새 RFC가 더 싸다.

## 팀 규칙

### 규칙

- 무엇: 코드, 문서, 브랜치, 커밋, PR을 어떻게 쓰나. 팀원이 겪는 것.
- 어디: `CONTRIBUTING.md`(입구)와 `docs/contributing/`.
- 바꾸는 방법: 그 파일을 고치는 PR. 정족수는 아래 "규칙 개정".

### 근거

- 되돌리는 것이 파일 한 줄이라 diff가 곧 기록이다.
- RFC에 넣었을 때 이름 표 한 행을 고치려고 새 RFC가 필요했다(RFC-001 표 80행).

### 검토한 대안

- 팀 규칙도 RFC (RFC-000 현행): 규칙 한 행을 고치려면 새 RFC나 부분 대체. RFC가 결정보다 규칙이 길어진다.
- 조직 전용 레포(`.github`): 다른 레포가 활동이 없다. 레포 하나에 두는 것이 링크와 리뷰가 단순하다.
- `docs/rules/`: GitHub 검색상 린터 규칙 문서 폴더가 대부분. 기여 규칙은 `docs/contributing/`이 관례다.

## 정책

### 규칙

- 무엇: 방향 안의 세부 규칙과 값. 인보이스 확정 대기 기간처럼 도입사가 겪는 값.
- 어디: `docs/policies/`.
- 바꾸는 방법: 그 값을 쓰는 코드와 같은 PR.

### 근거

- 값과 코드가 따로 바뀌면 문서와 동작이 어긋난다.
- 같은 PR이면 리뷰어가 둘을 한 번에 본다.

### 검토한 대안

- 정책도 RFC: 값 하나 바꾸는 데 전원 승인과 새 문서가 든다. 값은 되돌리면 그대로 돌아온다.

## 외부 계약

### 규칙

- 무엇: 백엔드 밖(도입사, 프론트엔드)이 의존해도 된다고 약속하는 것. 응답 필드, 오류 `code`, 상태 코드, 이벤트 필드.
- 어디: `backend/openapi.yaml`의 description. 정책 파일은 위치만 가리킨다.
- 모양을 바꾸는 것은 RFC.
- 모양을 채우는 것(새 엔드포인트, 새 오류 코드)은 일반 PR.
- 외부 계약이 얼어붙기 전은 아래 "외부 계약이 얼어붙는 시점".

### 근거

- 목록의 정본이 둘이면 어긋난다.
- openapi.yaml은 빌드가 다시 만들고 프론트엔드가 읽는 파일이라 여기서 어긋나면 바로 드러난다.

### 검토한 대안

- 오류 코드 목록을 정책 문서에 표로: openapi.yaml과 두 곳이 되어 어긋난다.
- 엔드포인트나 오류 코드마다 RFC: 모양을 채우는 것은 결정이 아니다. 모양은 한 번 정하면 된다.

## 시스템 구성

### 규칙

- 무엇: 서버, 배포, 노출 포트, 설정값.
- 어디: 그 디렉터리 README와 설정 파일.
- 바꾸는 방법: 설정 PR.

### 근거

- 서버가 겪는 것이라 팀 규칙도 정책도 아니다.
- 설정 파일이 정본이고 README는 실행법이다.

### 검토한 대안

- `docs/`에 운영 문서 폴더: 설정 파일과 두 곳이 된다. README는 그 디렉터리에 있어 같이 고쳐진다.

## 코드

### 규칙

- 무엇: 실제 적용값과 구현.
- 어디: 소스와 테스트.
- 바꾸는 방법: 일반 개발.
- 그 위에 서는 코드가 없고 리팩토링 PR 하나로 되돌아가는 설계 합의는 코드로 보여 주는 `proposal` PR.

### 근거

- 결정도 규칙도 아닌 것은 코드와 테스트가 정본이다.
- 내부 설계는 PR 본문과 리뷰가 기록이다.

### 검토한 대안

- 내부 설계 합의도 RFC: 되돌리는 것이 리팩토링 PR 하나라 얼릴 이유가 없다. 크기가 커도 그 위에 서는 것이 없으면 비용이 아니다.

## 그 밖의 위치

- 작업 범위와 진행 상태: Jira 티켓(스토리, 태스크, 서브태스크).
- 회의록, 일정, 브레인스토밍 초안: Miro.
- `docs/`에는 `rfcs/`, `policies/`, `contributing/`만 둔다.

## 가르는 기준

### 규칙

- 먼저 바꾸면 누가 겪는지 묻는다. 도입사면 정책이나 외부 계약이나 RFC, 팀원이면 규칙, 서버면 시스템 구성.
- 그 다음 되돌리면 무엇이 같이 움직이는지로 가른다.
- 한 내용을 두 곳에 쓰지 않는다. 정본이 아닌 곳(CLAUDE.md, 각 README)에서 언급해야 하면 정본을 가리킨다.
- 위에 없는 종류의 문서는 만들기 전에 어디에 둘지 먼저 합의한다.

| 질문 | 예이면 |
|---|---|
| 되돌리면 외부 계약(`openapi.yaml`에 나타나는 것)이 같이 바뀌거나 이미 쌓인 데이터를 다시 써야 하는가? | RFC |
| 되돌리면 `build.gradle`의 의존성이 바뀌거나 도메인 패키지 전부가 같은 방향으로 고쳐지는가? (도구가 대신 하는 기계적 변경은 제외) | RFC |
| 그 위에 서는 코드가 없고 리팩토링 PR 하나로 되돌아가는 설계인가? | proposal PR |
| 코드, 문서, 브랜치, PR을 쓰는 방법인가? 되돌리면 파일 한 줄인가? | 팀 규칙 |
| 값 하나(숫자, 길이, 기간, 켜고 끄기)만 바뀌고, 값을 되돌리면 그대로 돌아오나? | 정책 |
| 둘 다 아니고 구현 세부인가? | 코드 |
| 정하는 것이 아니라 하는 일인가? | Jira |

| 예 | 되돌리면 움직이는 것 | 위치 |
|---|---|---|
| 이벤트 스키마의 모양, 오류 응답의 모양, id 타입, 금액 정밀도 | 도입사가 보내는 것, 프론트 계약, 쌓인 행 | RFC |
| 새 엔드포인트, 새 오류 코드, 새 테이블 | 모양을 채우는 것이라 아무것도 | 일반 PR |
| JPA 대신 jOOQ, JUnit 대신 TestNG, 도메인 로직이 사는 층 | 그 위에 선 코드 전체 | RFC |
| 예외 핸들러를 글로벌로 둘지 도메인별로 둘지, 예외 클래스 계층 | 핸들러만. 리팩토링 PR로 되돌아간다 | proposal PR |
| 이름 규칙 표의 한 행, 주석 규칙, PR 상한 300줄 | 파일 한 줄 | 팀 규칙 |
| 노션 대신 레포, Jira 대신 GitHub Issues | 문서와 티켓의 위치 | 팀 규칙 ("문서의 정본" 표) |
| 인보이스 확정 대기 기간 며칠 | 상수 하나 | 정책 |
| 주석 재고를 전수 정리한다 | 작업이지 결정이 아님 | Jira 스토리 |
| Zoom 대신 Webex | 아무것도 | 슬랙에서 정하고 끝 |

- RFC 하나는 결정 하나다. 그 결정을 뒤집으면 문서 전체가 뒤집혀야 한다.
- 따로 바꿀 수 있는 항목이 섞여 있으면 그것은 규칙이므로 규칙 파일로 뺀다.
- RFC는 모양을 정하고, 그 모양을 채우는 것은 일반 PR이다.
- 애매하면 규칙이나 정책 PR로 올리고, 리뷰에서 "RFC급" 지적이 나오면 닫고 RFC로 승격한다.

### 근거

- 크기는 기준이 아니다. 여러 모듈을 건드려도 그 위에 서는 코드가 없으면 리팩토링 PR로 되돌아간다.
- 이름 바꾸기처럼 도구가 대신 하는 기계적 변경은 파일 수와 무관하게 되돌리는 비용이 없다.
- 이름이 "도구"인지 "규칙"인지도 기준이 아니다. JUnit은 도구지만 모든 테스트가 그 위에 서고, Zoom은 도구지만 그 위에 서는 것이 없다.

### 검토한 대안

- 중요하면 RFC: "중요"는 사람마다 다르다. 기준이 흐려지고 정본이 둘이 된다.
- 여러 모듈이 같이 바뀌면 RFC: 크기를 재게 된다. 이름 규칙 변경은 전 파일을 건드리지만 되돌리는 비용이 없다.
- 외부 계약과 데이터만 RFC (기술 선택 제외): JPA, JUnit, 레이어 규칙처럼 코드 전체가 기대는 선택이 빠진다. ADR이 원래 남기던 것이다.

## 토의 위치

### 규칙

| 단계 | 위치 |
|---|---|
| 초안 전. "이런 규칙이 필요한가", 작업 범위 합의, 찬반 | GitHub Discussions. 댓글 추천으로 가르고, 정식 집계가 필요하면 투표 카테고리 |
| 초안이 생긴 뒤 | 그 PR의 줄 댓글. 본문에 Discussion 링크를 단다 |
| 결론 | 규칙이면 파일 머지, 작업이면 Jira 티켓 설명에 결론과 링크 |
| 알림 | 슬랙. 토의는 하지 않고 링크만 |

- Discussion은 토의 위치이지 정본이 아니다. 결론은 PR이나 티켓으로 박히고, Discussion에만 있는 결정은 없다.

### 근거

- 슬랙 스레드는 흘러가고 찬반이 세어지지 않는다.
- PR 줄 댓글은 초안이 있어야 달린다.
- 그 사이의 "이게 필요한가"를 받을 위치가 Discussions다.

### 검토한 대안

- 초안 전 토의를 슬랙 스레드에서: 흘러가고 찬반이 집계되지 않는다.
- 초안 전 토의도 Jira 티켓 댓글에서: 티켓은 하는 일이지 정할 일이 아니다. 찬반 기능이 없다.

## 제안

### 규칙

- 방향 결정은 RFC PR. 쓰는 법은 `docs/rfcs/README.md`. 정족수는 작성자를 제외한 전원.
- 팀 규칙은 규칙 파일을 고치는 PR. 정족수는 아래 "규칙 개정".
- 합의가 안 된 변경은 라벨 `proposal`을 붙이고 본문 첫 줄에 합의가 필요한 점을 적는다.
- 정책 변경은 코드와 같은 PR로 올리고 일반 PR과 같은 절차로 리뷰한다.
- 내부 설계 합의(핸들러 배치, 레이어 구조, 모듈 분리)는 코드로 보여 주는 `proposal` PR. 필요하면 Discussion을 먼저 연다.
- 작업 범위는 Jira 티켓. 합의가 필요하면 Discussion을 먼저 연다.
- Draft PR로 열지 않는다.

### 근거

- `proposal` 라벨은 알림이 가면서 "합의 전"이라는 표시가 된다.

### 검토한 대안

- 제안을 Draft PR로: 슬랙 알림이 가지 않아 팀이 보지 못한다.
- 가벼운 제안도 노션 제안서로 (RFC-000 이전): 코드와 떨어져 있어 링크가 끊기고 리뷰가 두 곳에서 일어난다.

## 규칙 파일

### 규칙

- `docs/contributing/`에 주제당 파일 하나. 주제는 따로 바뀌는 단위로 가르고, 규칙이 생길 때 파일을 만든다.
- 파일명은 영어 소문자와 하이픈.
- 파일은 규칙 절들, 근거, 검토한 대안 순.
- 근거와 검토한 대안은 파일 끝에 한 절씩 두거나, 절마다 한 단계 아래에 규칙, 근거, 검토한 대안 소제목 셋으로 붙인다. 이 파일은 절마다 붙이고, 파일 전체의 이유만 끝에 "이 파일의 근거"로 둔다.
- 규칙은 불릿 하나에 하나, 또는 표. 표 양식과 근거의 종류(명세, 도구 동작, 스타일 가이드, 관례)는 `naming.md`를 따른다.
- 근거는 이유 하나에 불릿 하나.
- 검토한 대안은 한 줄씩. 무엇을 왜 버렸는지.
- 이력 절은 두지 않는다. 언제 왜 바뀌었는지는 git log와 PR 본문이 정본.
- 옮겨 온 규칙도 같은 양식. 규칙 절은 CONTRIBUTING.md의 문장을 고치지 않고 그대로 옮긴다.
- 옮겨 온 규칙의 근거와 검토한 대안 절은 두되, 기록된 적이 없으면 "초기 규칙이라 기록 없음. 절을 고칠 때 채운다" 한 줄만 쓴다. 지어내지 않는다.
- 한시 규칙은 절 제목 끝에 "(한시 규칙)"을 붙이고, 규칙 절의 첫 불릿에 끝나는 조건을 적는다.
- 도구가 검사하는 규칙은 도구 이름과 설정 파일 위치를 적고 문장을 줄인다.
- 규칙이 문서에만 있고 어겨도 아무것도 실패하지 않으면, 문장을 늘리기 전에 도구로 옮길 수 있는지 본다.

### 근거

- 규칙만 있으면 "왜"에 답할 수 없고 바꿀 때 무엇을 다시 검토해야 하는지 모른다.
- 옮겨 온 규칙의 근거를 지금 채우면 그때의 근거가 아니라 지금 지어내는 근거가 된다.
- 이력 절은 커밋 메시지와 PR 본문의 복사라 빠지기 시작하면 믿을 수 없다.
- 한시 규칙이 제목에 드러나면 목차만 봐도 지울 절이 보이고, 끝나는 조건이 첫 줄에 있으면 지울 때 무엇을 확인할지 바로 안다.

### 검토한 대안

- 규칙마다 Pros, Cons, Decision (Google C++ Style Guide 방식): 규칙 추가 비용이 커져 제안서 쓰기가 된다. 근거와 대안을 절 단위로 붙이는 것으로 대신한다.
- 규칙만 두고 근거 없이 (Rust style guide, thoughtbot 방식): "왜"를 물을 때 답이 없다. 면접이든 새 팀원이든 같은 질문을 한다.
- 이력 절 (KEP Implementation History): 커밋 메시지와 PR 본문에 이미 왜와 변경 사항이 있다. 손으로 베끼면 빠지기 시작하고 그때부터 믿을 수 없다.
- 옮기면서 근거를 채운다: 지어내게 된다. 이동과 내용 변경이 섞여 diff도 읽히지 않는다.

## 규칙 개정

### 규칙

| 변경 | 절차 |
|---|---|
| 오탈자, 죽은 링크, 예 보충, 표현 | 일반 PR. 티켓 없이 간다 |
| 값이나 행이 바뀐다 (상한 조정, 행 추가, 예외 추가) | PR 1명 승인 |
| 절이 새로 생기거나 없어진다, 방향이 바뀐다 | PR 전원 승인. 근거와 대안을 같이 고친다 |
| 끝나는 조건이 적힌 한시 규칙을 조건이 충족된 뒤 지운다 | PR 1명 승인. 조건이 충족됐다는 링크(닫힌 스토리, 머지된 PR)를 본문에 적는다 |
| CI에서 실패하게 만드는 검사 도구를 새로 붙인다 | PR 전원 승인. 규칙 표의 검사 열과 근거를 같이 고친다. 있는 검사에 규칙 한 줄 추가는 행 추가와 같다 |

- RFC 파일은 고치지 않는다. 규칙이 RFC에서 나왔더라도 지금 규칙은 규칙 파일이고, RFC는 그때의 결정 기록이다.

### 근거

- 값 정정에 전원을 요구하면 고치지 않게 된다.
- 절 신설과 CI 검사 도구는 팀원 전부의 작업 방식을 바꾸므로 전원이다.
- 한시 규칙은 만들 때 끝나는 조건을 적는다. 조건 충족은 방향 변경이 아니라 예정된 일이라 절 삭제여도 전원이 필요 없다.

### 검토한 대안

- 규칙 변경 전부 전원 승인: 값 정정도 전원이면 고치지 않게 된다.
- 규칙 변경 전부 1명 승인: 절 신설이 한 사람 눈으로 지나간다. 팀원 전부가 겪는 변경이다.

## RFC를 뒤집을 때

### 규칙

- 옛 파일을 지우지 않고 새 RFC를 쓴다.
- 새 문서의 frontmatter `supersedes`에 옛 번호를, 옛 문서에 `status: superseded`와 `superseded-by`를 적는다.
- 옛 문서 수정은 새 RFC의 PR에서 같이 한다.
- 일부만 뒤집는 일은 생기지 않아야 한다. 생겼다면 옛 RFC에 결정이 둘 섞여 있던 것이므로, 새 RFC가 어느 결정을 대체하는지 본문에 적고 옛 RFC는 그대로 둔다.

### 근거

- 되돌리는 비용이 큰 결정은 뒤집은 이유도 한 장으로 남아야 한다.

### 검토한 대안

- 옛 RFC 본문에 취소선이나 "일부 대체" 표시: 옛 문서를 읽는 사람이 어느 줄이 살아 있는지 알 수 없다. 결정 하나에 한 장이면 일부 대체가 생기지 않는다.
- 옛 RFC 삭제: "그때 왜 그랬나"가 사라진다.

## 외부 계약이 얼어붙는 시점

### 규칙

- 첫 도입사 연동 전까지는 이미 나간 모양을 바꾸는 것도 `proposal` PR로 낸다.
- 연동이 시작되면 모양 변경은 RFC.
- 연동 뒤 도입사에게 약속하는 유예 기간과 버전 방식은 이 파일이 아니라 정책이 정한다.

### 근거

- 연동 전에는 되돌려도 팀 밖에서 움직이는 것이 없다.
- 유예 기간과 버전 방식은 도입사가 겪는 값이라 정책이다.

### 검토한 대안

- 처음부터 모양 변경은 RFC: 도입사가 없는 동안 아무도 겪지 않는 비용에 전원 승인을 든다.
- v1 태그를 동결 시점으로: 태그는 우리가 붙이는 것이라 도입사가 기대기 시작하는 시점과 다를 수 있다. 연동이 더 정확하다.

## 이 파일의 근거

- 결정과 규칙은 되돌리는 비용이 다른데 RFC 한 파일에 같이 들어 있었다. RFC-003은 353줄 중 결정이 한 문단이었다. 얼어붙는 것과 살아 있는 것을 파일로 가른다.
- 결정 기록은 RFC-000(결정 기록을 레포에 둔다)과 RFC-003(RFC 기준을 좁힌다)다.
- 층마다 정본을 하나로 두면 어긋날 곳이 없다. 어디에 쓸지 고민하는 시간이 줄고, 찾는 사람은 한 곳만 본다.
