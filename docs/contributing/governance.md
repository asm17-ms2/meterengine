# 결정과 규칙의 위치와 개정

## 정본

- 이력이 남아야 하는 결정과 규칙은 레포, 흘러가도 되는 것은 Miro다.
- 표에 없는 문서는 만들기 전에 어디에 둘지 먼저 합의한다.

| 종류 | 정본 |
| --- | --- |
| 중요한 아키텍처 결정 | `docs/adr/` (쓰는 법은 그 README). 기존 RFC 기록은 `docs/rfcs/`에 보존 |
| 방향 안의 값(정책) | `docs/policies/` (도메인당 파일 하나, 쓰는 법은 그 README) |
| 스프린트 범위 | Jira(MS2 프로젝트)의 스프린트 |
| 회의록, 일정, 브레인스토밍 초안 | Miro |
| API 계약 | `backend/openapi.yaml` (컨트롤러와 DTO에서 자동 생성) |
| 팀 규칙 | `CONTRIBUTING.md`(입구)와 `docs/contributing/` (주제당 파일 하나) |
| 결정과 규칙을 어디에 두고 어떻게 바꾸나 | 이 파일 |
| 브랜치, 커밋, 머지 방식, 릴리스 | `git-workflow.md` |
| 머지 조건, PR 크기, 쪼개기, 스택, 리뷰 | `pull-request.md` |
| 문서 공통 규칙, 시간이 지나면 틀리는 값, README 점검 | `documents.md` |
| 이름 규칙 | `naming.md` |
| 오류 code, 문구, 예외와 핸들러의 자리 | `error-handling.md` |
| 주석과 javadoc | `comments.md` |
| 각 디렉터리의 실행법과 구조 | 그 디렉터리의 `README.md` |

## 가르는 기준

- 아래 범위에서 아키텍처에 중요한 영향을 주는 선택은 ADR로 기록한다.
- 기능 요구사항, 정책과 개발 절차 안의 아키텍처 결정도 대상이다. 분류 이름, 규모나 변경 비용만으로 판단하지 않는다.
- 다른 선택을 하면 이후 설계와 동작이 어떻게 달라지는지, 담당자가 어떤 선택 이유와 제약을 이해해야 하는지 함께 본다.

| 범위 | 다루는 선택 |
| --- | --- |
| 구조 | 구성요소, 데이터 모델과 책임의 경계 |
| 비기능 특성 | 성능, 보안, 가용성과 장애 복구에 관한 보장과 설계 선택 |
| 의존성 | 구성요소의 연결과 결합 방식 |
| 인터페이스 | API와 외부에 공개하는 계약 |
| 구현 기법 | 라이브러리, 프레임워크, 도구와 공통 개발 방식 |

| 질문 | 예이면 |
| --- | --- |
| 아키텍처에 중요한 영향을 주는 선택인가? | ADR |
| 코드, 문서, 브랜치, PR을 쓰는 방법인가? 되돌리면 파일 한 줄인가? | 팀 규칙 |
| 값 하나(숫자, 길이, 기간, 켜고 끄기)만 바뀌고, 값을 되돌리면 그대로 돌아오나? | 정책 |
| 기존 결정을 적용하는 구현 세부인가? | 코드 |
| 정하는 것이 아니라 하는 일인가? | Jira |

| 예 | 판단할 내용 | 위치 |
| --- | --- | --- |
| 이벤트 스키마의 모양, 오류 응답의 모양, id 타입, 금액 정밀도 | 공개 계약과 데이터 처리에 중요한 영향을 주는 설계 선택 | ADR |
| 새 엔드포인트, 새 오류 코드, 새 테이블 | 기존 결정을 적용하며 새로운 중요한 아키텍처 선택이 없음 | 일반 PR |
| JPA 대신 jOOQ, JUnit 대신 TestNG, 도메인 로직이 사는 층 | 의존성이나 구성요소의 책임에 중요한 영향을 주는 선택 | ADR |
| 예외 핸들러 배치, 예외 클래스 계층 | 중요한 아키텍처 선택인지, 기존 합의 범위 안의 구현인지 판단 | ADR 또는 일반 PR |
| 이름 규칙 표의 한 행, 주석 규칙, PR 상한 300줄 | 파일 한 줄 | 팀 규칙 |
| 인보이스 확정 대기 기간 며칠 | 상수 하나 | 정책 |
| 주석 재고를 전수 정리한다 | 작업이지 결정이 아님 | Jira 스토리 |
| Zoom 대신 Webex | 회의 도구의 교체 | 슬랙에서 정하고 끝 |

- ADR 하나는 한 중요한 결정이다. 독립적으로 채택하거나 대체할 결정은 나눈다.
- 애매하면 규칙이나 정책 PR에서 ADR 필요성을 확인하고, 중요한 아키텍처 선택이면 ADR을 준비해 연결한다.

## 층마다 바꾸는 방법

| 층 | 무엇 | 어디 | 바꾸는 방법 |
| --- | --- | --- | --- |
| ADR | 아키텍처에 중요한 영향을 주는 선택의 배경, 이유와 결과 | `docs/adr/` | 작성, 채택과 대체는 그 README. 정족수는 작성자를 뺀 전원 |
| 팀 규칙 | 코드, 문서, 브랜치, 커밋, PR을 쓰는 법 | `CONTRIBUTING.md`와 `docs/contributing/` | 그 파일을 고치는 PR. 정족수는 아래 "규칙 개정" |
| 정책 | 방향 안의 값. 도입사가 겪는 값 | `docs/policies/` | 그 값을 쓰는 코드와 같은 PR |
| 외부 계약 | 도입사와 프론트엔드가 의존하는 응답 필드, 오류 `code`, 상태 코드, 이벤트 필드 | `backend/openapi.yaml`의 description | 아키텍처에 중요한 영향을 주는 선택은 ADR. 기존 결정을 적용하는 변경은 일반 PR |
| 시스템 구성 | 서버, 배포, 포트, 설정값 | 그 디렉터리 README와 설정 파일 | 설정 PR |
| 코드 | 구현과 실제 적용값 | 소스와 테스트 | 합의한 범위 안의 구현과 내부 설계는 일반 PR에서 검토. 새로운 중요한 아키텍처 선택은 ADR |
| 작업 | 범위와 진행 상태 | Jira 티켓 | |

- `docs/`에는 `adr/`, 기존 기록을 보존하는 `rfcs/`, `policies/`, `contributing/`을 둔다.
- 연동 뒤 도입사에게 약속하는 유예 기간과 버전 방식은 정책이 정한다.

## 노션

- 노션은 쓰지 않는다. 무료 플랜으로 내려 수정하지 않는 채로 얼린다.
- 남은 내용은 옮기지 않는다. 작업하다 정책이나 ADR이 필요해지면 그때 새로 쓴다.

## 토의 위치

| 단계 | 위치 |
|---|---|
| 사전 합의가 필요하고 문서 초안이 없음 | GitHub Discussions. 의견을 모으고, 정식 집계가 필요하면 투표 카테고리 |
| 사전 합의가 필요하고 문서 초안이 있음 | 해당 문서 PR에서 논의하고 합의. 같은 결정의 Discussion을 중복 생성하지 않음 |
| 이미 합의한 범위 안의 구현과 내부 설계 | 일반 구현 PR에서 검토 |
| 논의 결론 | Discussion의 최종 합의 댓글이나 같은 결론을 확정한 결정 문서와 PR |
| 적용과 작업 | 규칙과 정책은 정본에 반영하고, 작업이면 Jira 티켓 설명에 결론과 링크 |
| 알림 | 슬랙. 토의는 하지 않고 링크만 |

- Discussion은 논의와 합의의 기록이다. 현재 적용할 규칙과 정책은 정본 문서에, 작업 범위와 진행 상태는 Jira에 반영한다.

### 제안 입력 양식

- 입력 항목과 필수 여부는 [제안 양식](../../.github/DISCUSSION_TEMPLATE/제안.yml)을 따른다.
- "합의할 점"을 생략하면 제안 내용 전체의 채택을 요청하는 것으로 본다.
- 아직 확인하지 못한 내용은 표시할 수 있다. 모든 조건과 테스트 목록을 정한 뒤에야 제안할 수 있는 양식으로 만들지 않는다.
- 단순 도구나 절차 변경에는 해당하지 않는 제품 동작과 테스트 항목을 요구하지 않는다. 구체적인 테스트 방법과 코드는 구현 과정에서 정한다.
- 문서 초안 PR에서 같은 결정을 검토하고 있다면 그 PR에서 논의를 이어갈 수 있다.

### Discussion의 범위와 분리

- 한 Discussion에서는 하나의 핵심 제안이나 아이디어와 적용 범위를 다룬다. 그 제안을 판단하는 데 필요한 설계 선택, 요구사항과 정책은 함께 논의할 수 있다.
- 다음 경우에는 분리를 검토한다.
  - 목적이나 적용 범위가 달라지는 경우.
  - 특정 쟁점만으로 상당한 대안 비교와 영향 검토가 필요하고, 나머지 내용과 구분해 논의할 수 있는 경우.
  - 항목별로 정리해도 여러 쟁점이 섞여 어떤 내용에 대한 의견이나 결론인지 따라가기 어려운 경우.
- 분리한 글은 서로 연결하고, 원래 제안에서 어떤 쟁점을 옮겼으며 그 결론이 전체 제안의 확정에 필요한지도 표시한다.

### 논의 후 결론

- Discussion에서 결론을 정하면 제안자가 최종 합의안을 별도 댓글에 정리한다. 아래 중 해당하는 내용을 담고, 해당하지 않는 항목은 생략한다.

```markdown
## 최종 합의안

### 합의한 내용의 제목

- 결정과 이유: 무엇을 하기로 했으며 왜 선택했는지.
- 적용 범위: 적용 대상과 제공할 내용.
- 조건과 예외: 필요한 업무 기준과 화면 및 API의 기대 동작.
- 검증 기준: 핵심 상황의 입력 조건과 기대 결과.
- 제외 범위와 후속 작업: 이번에 정하지 않거나 적용하지 않을 내용, 이어서 할 작업.
- 관련 기록: 필요한 결정 문서, 정책과 규칙, Jira 작업과 PR의 링크.
```

- 관련 내용의 결정과 이유, 조건 등을 같은 곳에서 확인할 수 있도록 내용별로 묶어 정리한다. 짧고 연결된 내용은 함께 적고, 길어지면 내용별로 댓글을 나누고 서로 연결한다.
- 팀원은 해당 최종 합의 댓글에 답글을 달거나 고정 링크로 어느 최종안에 동의하는지 표시한다. 여러 댓글로 나눴다면 동의하는 대상도 확인할 수 있도록 표시한다.
- 확정에 필요한 동의 인원과 조건은 해당 사안에 적용되는 팀 규칙을 따른다.
- 동의가 확인된 뒤 본문에 최종 합의 댓글 링크, 합의 날짜와 관련 작업을 추가한다.
- ADR이나 문서 PR에서 같은 결론을 확정했다면 그 기록을 연결하고, 같은 내용을 최종 합의 댓글에 복사하지 않는다.
- 기각하거나 보류한 제안도 결론과 이유를 표시한다. 변경 전 결론과 동의 기록은 보존한다.
- 합의와 구현 완료를 구분한다. 최종 합의 댓글은 논의 후 수동으로 작성하며, 처음 제안할 때 이미 합의가 끝난 것처럼 입력하도록 요구하지 않는다.

## 제안

- 중요한 아키텍처 결정은 ADR PR. 쓰는 법은 `docs/adr/README.md`.
- 팀 규칙은 규칙 파일을 고치는 PR. 정책은 코드와 같은 PR.
- 사전 합의가 필요한 사안의 논의 위치는 위 "토의 위치"를 따른다. 문서 PR에서 논의할 쟁점은 본문에 적고, 기존 합의가 있으면 그 기록을 연결한다.
- 이미 합의한 범위 안의 코드 구조와 테스트 구성은 구현 PR에서 검토한다.
- 구현 중 목적, 범위, 정책이나 계약을 바꾸려면 해당 부분을 구현하기 전에 다시 합의한다. 새로운 중요한 아키텍처 선택은 ADR로 기록한다.
- 사전 합의는 구현 PR의 리뷰, 필수 승인과 검사를 대신하지 않는다.
- Draft PR로 열지 않는다.

## 규칙 파일

- `docs/contributing/`에 주제당 파일 하나. 파일명은 영어 소문자와 하이픈.
- 규칙만 둔다. 근거, 검토한 대안, 이력 절, 출처 링크는 두지 않는다. 규칙 개정의 이유는 커밋 본문, 중요한 아키텍처 선택의 이유는 ADR에 기록한다.
- 양식은 `documents.md`.
- 한시 규칙은 제목 끝에 "(한시 규칙)"을 붙이고 첫 불릿에 끝나는 조건을 적는다.
- 도구가 검사하는 규칙은 도구 이름과 설정 파일 위치만 적는다.
  - 어겨도 아무것도 실패하지 않는 규칙은 문장을 늘리기 전에 도구로 옮길 수 있는지 본다.

## 규칙 개정

- 규칙 파일(`CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md`, `docs/contributing/`, `docs/README.md`)은 보호 경로라 어떤 변경이든 전원 승인이다. main 룰셋이 강제한다.
- 채택하거나 기각한 ADR과 기존 RFC의 당시 배경과 판단은 보존한다. 현재 규칙은 규칙 파일에서 관리한다.

| 변경 | 승인 외에 하는 것 |
|---|---|
| 오탈자, 죽은 링크, 예 보충, 표현 | 없다. 티켓 없이 간다 |
| 값이나 행이 바뀐다 (상한 조정, 행 추가, 예외 추가) | 없다 |
| 절이 새로 생기거나 없어진다, 방향이 바뀐다 | 커밋 본문의 왜에 검토한 대안을 적는다 |
| 끝나는 조건이 적힌 한시 규칙을 지운다 | 조건이 충족됐다는 링크(닫힌 스토리, 머지된 PR)를 본문에 적는다 |
| CI에서 실패하게 만드는 검사 도구를 새로 붙인다 | 그 규칙에 도구 이름과 설정 파일 위치를 적는다 |

## 결정을 대체할 때

- 새 ADR을 작성하고 `docs/adr/README.md`의 "대체"를 따른다. 기존 RFC도 같은 안내에 따라 연결하며 당시 본문과 번호는 보존한다.
