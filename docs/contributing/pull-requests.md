# PR 크기와 쪼개기

리뷰가 읽기 편한 단위가 기준이다. 줄 수는 상한이지 목표가 아니다.

- **하한은 없다.** 1줄 PR도 낸다. 함수명 변경처럼 기계적인 작업도 단일 기능이 아니면 나눈다
- **상한은 300줄이다.** 추가된 줄(+)을 테스트까지 포함해 센다. 빼고 세는 것은 아래뿐이다
  - 생성물: `backend/openapi.yaml`, 잠금 파일
  - 삭제된 줄
- 순수 삭제는 상한을 받지 않는다. 지우는 근거는 PR 본문에 적는다
- 삭제가 추가보다 큰 재작성은 리뷰어가 지운 것과 새로 쓴 것을 둘 다 읽어야 하므로, 상한과 별개로 더 잘게 나눈다
- 생성물이 diff에 올라왔는지는 리뷰에서 본다. CI가 검사하지 않는다 (CLAUDE.md "OpenAPI 생성물")
- **테스트는 기능과 같은 PR에 둔다.** 테스트만 있는 PR은 이미 머지된 코드의 테스트를 보강할 때로 한정한다
- **초과**: `backend/`, `.github/`, `deploy/`는 초과하지 않는다. `frontend/`, `demo/`는 작성자 판단으로 넘길 수 있고 PR 본문에 이유를 적는다
- **PR 하나당 서브태스크 하나.** 300줄을 넘길 것 같으면 티켓부터 쪼갠다

## 티켓 없이 가는 작업

오타, 죽은 링크, 포맷, 액션이나 의존성 버전 올리기는 Jira 티켓 없이 PR로 올린다. 가르는 기준은 나중에 Jira에서 되짚을 일이 있는지다.

- **티켓을 만든다**: 동작이나 정책이 바뀌는 것, 왜 했는지 diff 밖에 설명이 필요한 것, 스프린트 범위나 진행 상황으로 추적해야 하는 것
- **그냥 올린다**: 결과가 diff에 다 드러나고, 무엇을 왜 했는지 커밋 메시지 한 줄로 끝나는 것

애매하면 티켓을 만든다. 티켓 없이 올릴 때도 왜 했는지는 PR 본문에 적고, 브랜치명은 `docs/fix-readme-link`처럼 `<type>/<설명>`으로 쓴다.

## 쪼개는 축

층은 최소 단위가 아니다. 컨트롤러 하나가 엔드포인트 여러 개이고, 통합테스트 파일 하나가 독립된 `@Test` 여러 개다. 위에서부터 적용한다.

1. **동작별** - 엔드포인트나 화면 동작 하나 + 그 동작이 처음 쓰는 DTO/예외 + 그 동작의 테스트. 기본 축이다
2. **층별** - 동작이 하나뿐인데 크면 모델 / 서비스 / 컨트롤러. 새 도메인 모델을 들여올 때
3. **경로별** - 그래도 넘으면 성공 경로 / 검증 실패 / 동시성. 통합테스트가 마지막 조각에 몰릴 때

**바닥은 관찰 가능한 동작 하나다.** DTO만 있는 PR이나 검증 로직만 떼낸 PR은 호출되는 곳이 없어 리뷰어가 모양이 맞는지 판단할 수 없다.

고객 CRUD(전체 1593줄)를 동작별로 자른 예다. 테스트를 포함한 값이다.

| 조각 | 줄 |
| --- | --- |
| 엔티티 + 리포지토리 + 스키마 테스트 | 79 |
| GET 목록 + 응답 DTO + 테스트 | 200 |
| POST 등록 + 요청 DTO + 테스트 | 200 |
| PUT 수정 + 테스트 | 180 |
| DELETE + 예외 + 동시성 테스트 | 300 |

한 슬라이스가 여러 조각으로 나뉘면 스택 PR로 쌓는다. 머지 순서는 `stacked-prs.md`에 있다.
