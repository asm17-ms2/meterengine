# 결정과 규칙의 자리

무엇을 어디에 적고 어떻게 바꾸는지를 정한다. 왜 이렇게 나눴는지는 RFC-000과 RFC-005에 있다.

## 층

| 층 | 무엇 | 어디 | 바꾸는 방법 |
|---|---|---|---|
| RFC | 방향을 정하는 결정과 그 이유. 머지된 뒤에는 본문을 고치지 않는다 | `docs/rfcs/` | 새 RFC로 대체(supersede). 옛 RFC에는 상태와 대체 표시만 |
| 팀 규칙 | 코드, 문서, 브랜치, 커밋, PR을 어떻게 쓰나 | `CONTRIBUTING.md`(입구)와 `docs/contributing/` | 새 분야는 RFC 뒤 스택 PR, 있는 규칙의 정정은 proposal PR (아래 "규칙 신설"과 "규칙 개정") |
| 정책 | 방향 안의 세부 규칙과 값 | `docs/policies/` | 코드 PR과 같은 PR |
| 코드 | 실제 적용값 | 소스와 테스트 | 일반 개발 |

- Miro: 회의록, 일정, 브레인스토밍 초안 등 이력이 필요 없는 것
- 가벼운 Q&A: 슬랙
- `docs/`에는 `rfcs/`, `policies/`, `contributing/`만 둔다

한 내용을 두 곳에 쓰지 않는다. 정본이 아닌 곳(CLAUDE.md, 각 README)에서 언급해야 하면 정본을 가리킨다. 표에 없는 종류의 문서는 만들기 전에 어디에 둘지 먼저 합의한다.

## 가르는 기준

질문을 위에서부터 던진다. 처음 "예"가 나오는 층이 그 문서의 자리다.

| 질문 | 예이면 |
|---|---|
| 이걸 정한 뒤 나중에 바꾸려면 스키마, 다른 모듈, 외부 계약, 팀 규칙 중 하나라도 같이 바뀌거나, 데이터 이관이나 외부 공지가 필요한가? | RFC |
| 코드, 문서, 브랜치, PR을 쓰는 방법인가? | 팀 규칙 |
| 값 하나(숫자, 길이, 기간, 켜고 끄기)만 바뀌고, 값을 되돌리면 그대로 돌아오나? | 정책 |
| 둘 다 아니고 구현 세부인가? | 코드 |

주제가 아니라 "무엇이 바뀌는가"로 가른다. 같은 주제가 여러 층에 걸친다. 값을 바꾸는데 방식이 같이 바뀌면 RFC다. 대기 기간을 0일로 바꿔 대기 자체를 없애는 것은 값이 아니라 방식이 바뀐 것이다. 애매하면 정책 PR로 올린다. 리뷰에서 "RFC급" 지적이 나오면 닫고 RFC로 승격한다. 주제별 예시는 RFC-000 "가르는 기준"에 있다.

## 제안

- 방향을 바꾸는 것은 RFC PR로 올려 합의한 뒤 작업한다. 쓰는 법은 `docs/rfcs/README.md`. 정족수는 작성자를 제외한 전원
- 정책 변경은 코드와 같은 PR로 올리고 일반 PR과 같은 절차로 리뷰한다
- RFC를 쓰기엔 가벼운데 합의가 안 된 변경은 라벨 `proposal`을 붙여 바로 열고 본문 첫 줄에 합의가 필요한 점을 적는다. Draft로 열지 않는다. Draft PR은 슬랙 알림이 가지 않아 반대할 사람이 제안을 보지 못한다. 반대가 없으면 평소대로 리뷰하고 머지한다. 제안 PR만 모아 보려면 `label:proposal`로 거른다

## 규칙 신설

새 분야의 팀 규칙은 RFC로 정한다. 새 분야란 `docs/contributing/`에 파일이 새로 생기거나 기존 파일에 절이 새로 생기는 규모다. 이름 규칙(RFC-001)과 주석 규칙(RFC-002)이 그 예다.

- RFC에는 왜 그렇게 정했는지와 검토한 대안을 적는다. 규칙 본문이 표라면 RFC에도 표를 둔다
- 채택되면 규칙 본문을 `docs/contributing/` 파일로 옮기는 PR을 RFC PR 위에 스택으로 올린다. RFC PR 템플릿의 "같이 바뀌어야 하는 문서" 항목이 이것이다
- 규칙 파일에는 규칙, 예, 근거의 종류만 적는다. 이유는 한 절로 끝내고, 긴 이유는 RFC를 가리킨다. 표 양식과 근거의 종류(명세, 도구 동작, 스타일 가이드, 관례)는 `naming.md`를 따른다
- 도구가 강제하는 규칙은 도구 이름과 설정 파일 위치를 적고 문장을 줄인다. 규칙이 문서에만 있고 아무것도 실패하지 않으면 도구로 옮길 수 있는지 먼저 본다

## 규칙 개정

이미 있는 규칙을 고칠 때는 변경의 크기로 절차를 가른다. RFC 파일은 어느 경우에도 본문을 고치지 않는다.

| 변경 | 절차 | 옛 RFC |
|---|---|---|
| 오탈자, 죽은 링크, 예 보충, 표현 | 일반 PR. 티켓 없이 간다 | 그대로 |
| 방향은 그대로인데 값이나 행이 바뀐다 (상한 조정, 행 추가, 예외 추가) | proposal PR. 규칙 파일의 근거 칸에 그 PR 번호를 적는다 | 그대로 |
| 방향이 바뀐다 | 새 RFC. 규칙 파일 갱신은 그 위에 스택 PR | `status: superseded`와 `superseded-by`. 일부만 바뀌면 아래 "일부 대체" |

가르는 질문은 하나다. 옛 RFC의 "검토한 선택지"에서 버린 쪽을 고르는가. 그러면 방향이 바뀐 것이고 새 RFC다. 그 안에서 움직이면 proposal PR이다.

### 일부 대체

새 RFC가 옛 RFC의 결정 중 일부만 바꾸면 옛 RFC의 상태는 `accepted`로 두고, 두 곳에 표시한다.

- 새 RFC의 frontmatter `supersedes`에 번호와 바꾸는 항목을 적는다. 예: `supersedes: "000 (층 표, docs/ 폴더 구성)"`
- 옛 RFC의 제목 바로 아래에 한 줄을 넣는다. 예: `일부 대체: RFC-005가 층 표와 docs/ 폴더 구성을 대체한다.` 이 한 줄이 옛 RFC 본문에 손대는 유일한 경우다

옛 RFC의 수정은 새 RFC의 PR에서 같이 한다.
