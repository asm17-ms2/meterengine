# RFC-000: 문서와 결정 프로세스 도입

## 배경 및 문제 정의

기존 규칙은 결정 기록의 정본이 노션 MS2 팀 위키이고, 방향을 바꾸는 제안은 노션 제안서로 올리는 것이었다. 노션 제안서 ["[BE] API 키는 별도 테이블에 SHA-256 해시로 저장한다"](https://app.notion.com/p/3cd0899b32b8811d93a8e91c56999ed5)(2026-08-31)를 팀이 같이 검토하다가 확인한 문제:

- 리솔브된 댓글이 접혀 어떤 질문이 오갔는지 한눈에 안 보인다
- 본문을 수정하면 댓글의 문맥이 사라져 결정 이유를 추적할 수 없다
- 슬랙으로 건별 알림이 없어 검토 요청과 반응을 실제로 놓쳤다
- 승인 워크플로가 없어 "합의됐다"가 기록이 아니라 기억에 남는다
- 이와 별개로, 세부 규칙(입력 길이, 대기 기간 등)은 코드와 문서 중 어느 쪽이 맞는지 불분명하다

이 제안은 그 제안 절차 자체를 바꾸므로 새 형식(RFC PR)으로 올린다.

## 검토한 선택지

### A안. 노션 유지 + 결정 DB 템플릿

- 장점: 도구 변경 없음
- 단점: 댓글 접힘, 문맥 유실, 건별 슬랙 알림 없음, 승인 워크플로 없음. 원래 문제가 그대로다

### B안. 별도 저장소 (asm17-ms2/rfcs)

- 장점: PR 목록이 곧 결정 목록. 코드 PR과 안 섞인다
- 단점: 레포 왕복, 슬랙 구독과 브랜치 보호 이중 관리
- 저장소까지 만들었다가 왕복 비용이 크다고 보고 접었다. 라벨 필터로도 목록 섞임이 불편해지면 이 안으로 옮긴다. 파일은 그대로 이동하면 된다

### C안. GitHub Discussions만 사용

- 장점: 커밋 없이 토의, 답변 채택
- 단점: 문서 특정 줄에 질문을 못 붙인다. 본문과 토의가 분리된다

### D안. 토론 전용 도구 (Loomio, Kialo)

- 장점: 제안, 투표, 기록이 구조화된다
- 단점: 도구 추가, 줄 단위 토의 불가, 팀 규모에 과함

### E안. 메인 레포 docs/rfcs/ + docs/policies/

- 장점: 토의, 알림, 승인이 기존 슬랙 구독과 브랜치 보호를 그대로 탄다. 코드와 정책이 같이 움직인다. 레포도 도구도 늘지 않는다
- 단점: 코드 PR과 목록이 섞인다. 실시간 공동 편집이 없다

## 결정

선택한 것: "E안. 메인 레포 docs/rfcs/ + docs/policies/", 이유: 토의와 알림과 승인이 기존 슬랙 구독과 브랜치 보호를 그대로 타고, 코드와 정책이 같이 움직이며, 레포도 도구도 늘지 않는다.

문서를 세 층으로 나누고 모두 메인 레포에 둔다.

| 층 | 무엇 | 어디 | 바꾸는 방법 |
|---|---|---|---|
| RFC | 방향을 정하는 결정 | `docs/rfcs/` | 새 RFC로 대체(supersede) |
| 정책 | 방향 안의 세부 규칙 | `docs/policies/` | 코드 PR과 같은 PR |
| 코드 | 실제 적용값 | 소스와 테스트 | 일반 개발 |

- Miro: 회의록, 일정, 브레인스토밍 초안 등 이력이 필요 없는 것
- 가벼운 Q&A: 슬랙
- docs/에는 rfcs/와 policies/만 둔다

### 가르는 기준

질문을 위에서부터 던진다. 처음 "예"가 나오는 층이 그 문서의 자리다.

| 질문 | 예이면 |
|---|---|
| 이걸 정한 뒤 나중에 바꾸려면 스키마, 다른 모듈, 외부 계약, 팀 규칙 중 하나라도 같이 바뀌거나, 데이터 이관이나 외부 공지가 필요한가? | RFC |
| 값 하나(숫자, 길이, 기간, 켜고 끄기)만 바뀌고, 값을 되돌리면 그대로 돌아오나? | 정책 |
| 둘 다 아니고 구현 세부인가? | 코드 |

주제가 아니라 "무엇이 바뀌는가"로 가른다. 같은 주제가 세 층에 걸친다.

| 주제 | RFC: 방식 (괄호는 같이 바뀌는 것) | 정책: 값 (바꿔도 방식은 그대로) | 코드 |
|---|---|---|---|
| 인보이스 확정 | 확정 전 대기 기간을 두는가, 그동안 수정을 허용하는가 (invoice 상태 흐름, 결제 시점, 세금계산서 발행 시점) | 대기 기간이 며칠인가 | 일수 상수, "대기 중에는 확정되지 않는다" 테스트 |
| 미터 집계 | 이벤트를 건별로 합산하는가, 시간 창으로 묶는가 (pricing 계산식, invoice 라인) | 시간 창 크기, 늦게 도착한 이벤트를 받아 주는 시간 | 창 크기 상수, 집계 쿼리, 인덱스 |
| API 키 | 평문 저장인가 해시 저장인가 (발급 응답, 인증, 테이블, 기존 키 이관) | label 최대 길이, 고객당 키 개수 상한 | 해시 호출, 길이 검증, 테스트 |
| 결제 실패 | 자동 재청구인가 수동 처리인가 (payment와 invoice 상태 흐름) | 재시도 횟수와 간격 | 재시도 루프, 테스트 |
| 목록 API | offset인가 cursor인가 (외부 API 계약) | 페이지 크기 상한 (지금 100, `backend/openapi.yaml`이 정본) | size 파라미터 검증 |
| 이벤트 스키마 | 필드를 더하거나 뜻을 바꾸는가 (외부 수집 API 계약, 집계 쿼리, 저장 테이블) | transaction_id 최대 길이 (지금 255) | 스키마 검증, 테스트 |

값을 바꾸는데 방식이 같이 바뀌면 RFC다. 대기 기간을 0일로 바꿔 대기 자체를 없애는 것, 재시도 횟수를 0으로 바꿔 자동 재청구를 끄는 것은 값이 아니라 방식이 바뀐 것이다. 애매하면 정책 PR로 올린다. 리뷰에서 "RFC급" 지적이 나오면 닫고 RFC로 승격한다.

표의 예시는 종류를 보여 주는 것이고, 대기 기간을 둘지나 재청구 방식 같은 것은 아직 정하지 않았다.

### RFC (docs/rfcs/)

- PR 하나 = 제안 하나. `template.md`를 복사해 `NNN-short-english-title.md`. 제목은 영어 소문자와 하이픈만 쓴다. 번호는 세 자리, 재사용 없음. 이 문서가 000
- frontmatter `domain`에 그 결정을 바꾸면 무너지는 도메인을 적는다. 값은 process거나 백엔드 패키지명(customer, event, metric, pricing, invoice, payment). 여럿이면 리스트로 전부 적고 순서에 뜻을 두지 않는다. README 표의 도메인 열은 같은 값
- PR 제목 `RFC-NNN: 제목`, 라벨 `rfc`. 라벨은 이것 하나만 쓴다. type은 브랜치명과 제목 접두사에 이미 있다
- 전용 PR 템플릿 `.github/PULL_REQUEST_TEMPLATE/rfc.md`. 웹에는 템플릿 선택창이 없어 README의 링크 형식(`?template=rfc.md&labels=rfc`)으로 연다
- 토의는 줄 단위 댓글로. 유효한 반론은 작성자가 "검토한 선택지"에 옮겨 적는다
- 채택되면 같이 고쳐야 하는 문서나 규칙은 스택 PR로 준비한다. 이 제안의 CONTRIBUTING.md 개정이 첫 사례다
- 승인은 Approve, 정족수는 작성자를 제외한 전원. "당장은 넘어가도 된다"는 유보 동의도 Approve로 표시한다. 경로별 강제가 안 되므로 관례로 지킨다
- PR을 열 때 README 표에 draft로 한 줄 추가. 전원 승인 후 작성자가 frontmatter의 status와 date(결정이 마지막으로 바뀐 날)를 갱신하고 표의 상태와 날짜를 맞춘 뒤 squash merge
- 상태: draft -> accepted / rejected -> superseded. 채택하지 않기로 하면 같은 정족수로 status를 rejected로 바꾸고 기록용으로 merge
- 뒤집을 때 옛 파일을 지우지 않는다. 새 문서에 어느 결정을 대체하는지(`supersedes`), 옛 문서에 대체됨 상태(`status: superseded`)와 무엇으로 대체됐는지(`superseded-by`)를 적는다. 옛 문서 수정은 새 RFC의 PR에서 같이 한다

### 정책 (docs/policies/)

무엇을 적나
- 도메인당 파일 하나. 이름은 백엔드 패키지명: `customer.md`, `event.md`, `metric.md`, `pricing.md`, `invoice.md`, `payment.md`
- RFC가 정한 방향 안에서 실제로 적용되는 규칙과 값. 정책 파일이 값을 정하고 코드가 적용한다. 값 옆에 코드 위치와 이유를 적는다. 둘이 다르면 둘 중 하나가 버그다
- API 계약에 나가는 값(길이, 상한, 기본값)은 `backend/openapi.yaml`이 정본. 정책 파일은 그 위치를 가리키기만 한다

어떻게 적나
- `template.md`를 복사한다. 근거 RFC는 행마다 근거 칸에 적는다
- 주제마다 절 하나, 규칙 하나가 표 한 줄. 값, 코드 위치, 근거를 적고 표 아래에 왜 그 값인지 한 줄
- 코드 위치는 grep되는 이름으로 쓴다. 클래스.상수, 메서드, 테스트 이름, DB 제약 이름, openapi.yaml의 스키마 이름. 리뷰에서 실제로 grep되는지 확인한다
- 변경 이력은 두지 않는다. git log가 그 역할이다

어떻게 바꾸나
- 정책 변경은 코드 변경과 같은 PR. 일반 PR과 같은 절차로 리뷰한다
- 값을 바꾸는데 다른 모듈이 같이 바뀌면 RFC로 올린다. 기준은 위 "가르는 기준"
- 경계가 애매하면 정책 PR로 올린다. 리뷰에서 "RFC급" 지적이 나오면 닫고 RFC로 승격

첫 정책 문서를 쓸 때 참고할 예시. 제품에 없는 user 도메인을 지어낸 것이다.

````markdown
# user 정책

## 닉네임

| 항목 | 값 | 코드 위치 | 근거 |
|---|---|---|---|
| 길이 | 2자 이상 12자 이하 | `NicknamePolicy.MAX_LENGTH` | RFC-003 |
| 허용 문자 | 한글, 영문, 숫자. 공백과 특수문자 불가 | `NicknamePolicy.PATTERN` | RFC-003 |
| 중복 | 불가. 대소문자 구분 없음 | `users_nickname_key` 인덱스, `UserRepository.existsByNicknameIgnoreCase` | 초기 관례 |
| 변경 주기 | 30일에 1회 | `NicknameChangeService.CHANGE_INTERVAL_DAYS`, `NicknameChangeIntervalTest` | PR #NNN |

왜 12자: 프로필 카드 한 줄에 잘리지 않는 최대치. 프론트 레이아웃이 바뀌면 재검토.
왜 30일: 닉네임을 갈아타며 사칭하는 것을 막는다. 사칭 신고 기능이 생기면 완화 검토.

## 이메일

| 항목 | 값 | 코드 위치 | 근거 |
|---|---|---|---|
| 형식과 길이 | RFC 5322 기본 형식, 254자 이하 | `@Email`, `EmailPolicy.MAX_LENGTH` | 초기 관례 |
| 인증 기한 | 가입 후 24시간. 넘기면 로그인 제한 | `EmailVerificationService.EXPIRE_HOURS`, `EmailVerificationExpiryTest` | RFC-003 |

## 비밀번호

| 항목 | 값 | 코드 위치 | 근거 |
|---|---|---|---|
| 길이 | 8자 이상 64자 이하 | `PasswordPolicy.MIN_LENGTH`, `PasswordPolicy.MAX_LENGTH` | 초기 관례 |
| 구성 | 영문, 숫자, 특수문자 중 2종 이상 | `PasswordPolicy.validate`, `PasswordPolicyTest` | 초기 관례 |
| 해시 | bcrypt, cost 12 | `SecurityConfig.passwordEncoder` | RFC-003 |

왜 cost 12: 로그인 한 번에 250ms 안쪽이면서 무차별 대입에 버티는 값. 서버 사양이 바뀌면 재측정.
````

### 코드

- 정책이 정한 값을 코드 상수가 담고 테스트가 지킨다
- 문서와 코드가 어긋나면 둘 중 하나가 버그다. 어느 쪽이 의도인지 슬랙이나 팀 회의에 보고한 뒤 맞춘다

### 기존 문서 이관 (노션, javadoc, 주석)

- 노션 결정과 코드 안의 javadoc, 주석에 남은 설계 이유를 docs/로 옮길지, 어디까지 옮길지는 추후 결정

### 흐름

```
Miro/회의에서 아이디어 -> (반응 있으면) -> docs/rfcs/에 PR -> 줄 댓글 토의 -> Approve -> squash merge
                                                                  |
                                              구현 이슈 생성 -> 정책 파일 + 코드 PR
```

### 결과

- 좋은 점: 토의, 알림, 승인이 전부 기록으로 남는다. 코드와 정책이 한 레포에서 같이 움직인다
- 나쁜 점: 수정마다 커밋이 필요하고 실시간 공동 편집이 없다. 초안은 Miro에서 잡고 옮긴다
- 나쁜 점: 코드 PR과 목록이 섞인다. `rfc` 라벨로 거르고, 불편해지면 B안으로
- 나쁜 점: 모아보기가 노션보다 약하다. README 표로 시작, 수십 개 넘으면 MkDocs 등 검토

## 도입 절차

1. 스택 PR 두 개. 앞은 `docs/rfcs/`, `docs/policies/` 템플릿, `.github/PULL_REQUEST_TEMPLATE/rfc.md` 추가, 뒤는 CONTRIBUTING.md 개정("문서의 정본" 표의 정책과 결정 기록을 `docs/policies/`와 `docs/rfcs/`로, "제안" 항목에 RFC PR을 잇는다)과 이를 가리키는 CLAUDE.md, README.md 문구. gh stack 절차로 만든다
2. 팀 슬랙 채널 구독에 reviews와 comments 추가 (`/github subscribe asm17-ms2/meterengine reviews comments`). 기본 구독에는 없다
3. 비어 있는 asm17-ms2/rfcs 저장소를 아카이브한다
