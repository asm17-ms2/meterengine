# RFC-000: 문서와 결정 프로세스 도입

## 배경 및 문제 정의

기존 규칙은 결정 기록의 정본이 노션 MS2 팀 위키이고, 방향을 바꾸는 제안은 노션 제안서로 올리는 것이었다. 노션 제안서 ["[BE] API 키는 별도 테이블에 SHA-256 해시로 저장한다"](https://app.notion.com/p/3cd0899b32b8811d93a8e91c56999ed5)(2026-08-31)를 팀이 같이 검토하다가 확인한 문제:

- 리솔브된 댓글이 접혀 어떤 질문이 오갔는지 한눈에 안 보인다
- 본문을 수정하면 댓글의 문맥이 사라져 결정 이유를 추적할 수 없다
- 슬랙으로 건별 알림이 없어 검토 요청과 반응을 실제로 놓쳤다
- 승인 워크플로가 없어 "합의됐다"가 기록이 아니라 기억에 남는다
- 이와 별개로, 세부 규칙(입력 길이, 대기 기간 등)은 코드와 문서 중 어느 쪽이 맞는지 불분명하다

이 제안은 그 제안 절차 자체를 바꾸므로 새 형식(RFC PR)으로 올린다.

## 검토한 선택지

### A안. 노션 유지 + 결정 DB 템플릿

- 장점: 도구 변경 없음
- 단점: 댓글 접힘, 문맥 유실, 건별 슬랙 알림 없음, 승인 워크플로 없음. 원래 문제가 그대로다

### B안. 별도 저장소 (asm17-ms2/rfcs)

- 장점: PR 목록이 곧 결정 목록. 코드 PR과 안 섞인다
- 단점: 레포 왕복, 슬랙 구독과 브랜치 보호 이중 관리
- 저장소까지 만들었다가 왕복 비용이 크다고 보고 접었다. 라벨 필터로도 목록 섞임이 불편해지면 이 안으로 옮긴다. 파일은 그대로 이동하면 된다

### C안. GitHub Discussions만 사용

- 장점: 커밋 없이 토의, 답변 채택
- 단점: 문서 특정 줄에 질문을 못 붙인다. 본문과 토의가 분리된다

### D안. 토론 전용 도구 (Loomio, Kialo)

- 장점: 제안, 투표, 기록이 구조화된다
- 단점: 도구 추가, 줄 단위 토의 불가, 팀 규모에 과함

### E안. 메인 레포

- 장점: 토의, 알림, 승인이 기존 슬랙 구독과 브랜치 보호를 그대로 탄다. 코드와 정책이 같이 움직인다. 레포도 도구도 늘지 않는다
- 단점: 코드 PR과 목록이 섞인다. 실시간 공동 편집이 없다

## 결정

선택한 것: "E안. 메인 레포", 이유: 토의와 알림과 승인이 기존 슬랙 구독과 브랜치 보호를 그대로 타고, 코드와 정책이 같이 움직이며, 레포도 도구도 늘지 않는다.

이 결정이 정한 것은 결정과 규칙의 정본을 노션 대신 레포에 두는 것이다. 문서를 어떤 층으로 가르고 어디에 두고 어떻게 바꾸는지는 규칙이라 이 문서가 아니라 규칙 파일이 정본이다.

### 기존 문서 이관 (노션, javadoc, 주석)

- 노션 결정과 코드 안의 javadoc, 주석에 남은 설계 이유를 docs/로 옮길지, 어디까지 옮길지는 추후 결정

### 결과

- 좋은 점: 토의, 알림, 승인이 전부 기록으로 남는다. 코드와 정책이 한 레포에서 같이 움직인다
- 나쁜 점: 수정마다 커밋이 필요하고 실시간 공동 편집이 없다. 초안은 Miro에서 잡고 옮긴다
- 나쁜 점: 코드 PR과 목록이 섞인다. `rfc` 라벨로 거르고, 불편해지면 B안으로
- 나쁜 점: 모아보기가 노션보다 약하다. README 표로 시작, 수십 개 넘으면 MkDocs 등 검토
