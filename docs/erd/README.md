# 스키마와 ERD

DB 스키마 문서를 둔다 (MS2-26). 스키마 변경의 입구는 Flyway 마이그레이션이며, 이 폴더의 문서를 고쳐서 스키마를 바꾸는 경로는 없다.

## 무엇이 어디에 있나

| 경로 | 내용 | 누가 쓰나 |
|---|---|---|
| `generated/` | 컬럼, 제약, 인덱스, 트리거의 실제 정의와 ER 다이어그램 | tbls가 DB에서 |
| `erd.md` | 생성물이 대체하지 못하는 구간. 제약의 근거, 의도된 제외, 스토리별 이관 항목, 아직 테이블이 없는 엔티티 | 사람이 손으로 |
| `backend/src/main/resources/db/migration/V*.sql` | 스키마의 코드 정본 | 사람이 손으로 |

`generated/`는 마이그레이션의 렌더링이지 독자적인 문서가 아니다. **손으로 고치지 않는다** (다음 재생성에서 덮어써진다). 컬럼과 제약의 짧은 근거는 마이그레이션의 `COMMENT ON`에서 온다.

`erd.md`와 `generated/`가 어긋나면 정책의 정본은 `erd.md`다. 다만 `generated/`는 실제 DB에서 뽑은 것이라, 다르다는 사실 자체가 마이그레이션과 정책이 어긋났다는 신호다. 혼자 정하지 말고 팀에 알린다 (`erd.md`의 "이 문서와 generated/의 관계" 참조).

## 지위

tbls 전환은 MS2-31로 끝났다. 다이어그램과 컬럼/제약 목록은 `generated/`가 DB에서 뽑고, `erd.md`에서는 mermaid 다이어그램을 걷어냈다.

- 생성물에는 버전을 붙이지 않는다. DB의 현재 상태를 그대로 반영하므로 "어느 슬라이스까지 반영했는가"라는 질문이 성립하지 않는다. `docs/`의 다른 폴더에 적용되는 버전과 반영 범위 명시 규칙은 여기에 적용되지 않는다
- `erd.md`도 버전 번호를 붙이지 않는다. 개정 이력 표는 v2.2에서 동결했고 이후 변경은 git 히스토리로 추적한다 (MS2-31)
- `erd.md`에 남은 구간(제약의 근거, 의도된 제외, 스토리별 이관 항목)은 `docs/spec/`과 `docs/adr/`로 이관한다. **전환이 끝났으므로 이 이관은 이제 착수 가능하다.** 이관이 끝나면 이 폴더는 생성물 전용이 되고 직접 편집하지 않는다. 이관 대기 목록은 `docs/문서-관리-규칙.md`에 있다

## 새 제약을 정할 때

값은 `docs/spec/`, 근거는 `docs/adr/`에 쓴다. 판별은 `docs/문서-관리-규칙.md`의 Q1과 Q3을 따른다. 마이그레이션 SQL 주석에는 무엇을 하는지가 아니라 어느 문서가 근거인지를 적는다.

`COMMENT ON`도 같다. 한 줄로 근거 문서를 가리키는 데까지만 쓰고(결정 번호, 스토리 키, PR 번호), 상세는 그 문서에 둔다. 이 한 줄이 `generated/`의 설명 칸이 되므로 문서를 열지 않고도 어디를 봐야 하는지 알 수 있다.

## 다시 만들기

```
./scripts/generate-erd.sh
```

일회용 postgres 컨테이너에 마이그레이션을 적용하고 tbls로 뽑은 뒤 컨테이너를 버린다. docker만 있으면 되고 tbls를 로컬에 설치할 필요는 없다. 개발용 DB는 건드리지 않는다.

**마이그레이션을 바꿨으면 이 스크립트를 돌리고 생성물을 같은 커밋에 넣는다.** 빠뜨리면 CI의 `erd` job이 실패한다. `docs/api/generated`와 같은 계약이다 (`docs/api/README.md`의 "구현 스냅샷").

생성물을 커밋해 두는 목적은 그 파일을 읽으려는 게 아니라, PR diff에 스키마 변화가 드러나게 하기 위해서다. SVG는 컬럼 하나만 늘어도 좌표가 전부 바뀌므로 `.gitattributes`에서 접어 두었다. 읽을 것은 `.md` diff다.
